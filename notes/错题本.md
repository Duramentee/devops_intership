# 错题本

> **收什么**：答错、答不全、以及"答对了但机制说不清"的题。
> **不收什么**：已经能完整说出机制与验证方法的题（那些留在 `notes/weekN/dayN.md` 里）。
>
> **每一行四列**：题目 → **我的错答**（要避免的说法）→ **正确结论** → **错因**。
> **复查方式**：遮住「正确结论」列，只看题目与错答，口述正确答案；说不出来就在「复查记录」里记一次。
>
> **错因分类**
>
> | 码 | 含义 | 典型表现 |
> |---|---|---|
> | **A** | **概念混淆**：把两个不同层次的东西当成一件事 | 构建期 vs 运行期、对象层 vs 数据层、uid vs capability |

## 一、热身周 · Linux / Shell（Day 1，得分 27/60）

| # | 题目 | 我的错答（要避免） | 正确结论 | 错因 |
|---|---|---|---|---|
| L1 | `find` 复合条件：`/data` 下 `.tar.gz`、超过 30 天、大于 50MB，先看再删 | `find "/data/*.tar.gz" -mtime +30d -size +50m -exec rm -f {} +` | 路径只给起点目录、通配符交给 `-name '*.tar.gz'`；`-mtime +30`（不带 `d`）、`-size +50M`（大写 M）；要 `-type f`；`-delete` 是内置动作（不 fork、隐含 `-depth`），不是"快捷写法" | B |
| L2 | `for f in $(ls)` 有什么问题、怎么改；`rm $file` 与 `rm "$file"` 的差别 | "空目录会迭代空内容导致报错"；"变量内容可能被当作一个命令" | 问题是**分词/展开**（`$(ls)` 的输出经过 IFS 分词），与空目录无关（空目录循环体一次都不执行、**不报错**）；无引号时变量被拆成**多个参数**（不是"被当命令"）。改法：`for f in "$dir"/*` + `[ -e "$f" ] \|\| continue` | B |
| L3 | `df -h` 说 `/` 满，但 `du -sh /*` 只有一半，原因与定位 | "可能是日志文件占用过高" | **文件已被 `rm` 但进程仍持有 fd** → 空间不释放；定位：`lsof +L1` | D |
| L4 | nginx 日志按**每小时**统计请求数并倒序取前 5 | `cat log \| awk '{}' \| uniq -c \| tail -5`；想用 `for i in 24` 循环 | 一次遍历 + 关联数组：`awk '{split($4,t,":"); c[t[2]]++} END{for(h in c) print c[h],h}' log \| sort -rn \| head -5`。`uniq -c` 只合并**相邻**行，缺 `sort` 结果必错 | B / D |
| L5 | 硬链接与软链接：`rm` 原文件后 `cat` 各自的结果与原理 | 机制说对了，但漏术语"**链接计数**" | 硬链接 = 新增一条目录项指向同一 inode，**链接计数 +1**；删名只是计数 -1，数据仍在；软链接内容是指向路径的字符串，目标消失即断链 | B |
| L6 | 僵尸进程：产生、`ps` 状态、父进程该做什么、`kill -9` 能否解决 | 核心正确，漏"父进程先退出时由 init 收养" | 子进程已退出但父进程**未 `wait()`**；`STAT` 为 `Z`；治本 = 父进程 `wait()`；治标 = 结束父进程（**前提是父进程先退出**，内核才交 PID 1 回收）；僵尸无法用信号处理 | C |

### 1.1 Day 7 综合找 bug（得分 **5 / 10**）新增错题

> 原题：三处 bug —— ① 含空格文件名出错 ② 只影响效率 ③ 结果完全错

| # | 题目 | 我的错答（要避免） | 正确结论 | 错因 |
|---|---|---|---|---|
| L7 | `$(ls)` 为什么会把含空格文件名搞坏（**机制**） | "文件名中有空格或者特殊分隔符会导致识别错误成多个文件" —— 只描述了**现象**，没说**谁**在切、按**什么**切 | 切分者是 **shell**（不是 `ls`），发生在**命令替换之后**：对未加引号的替换结果做 **word splitting**，分隔符 = `IFS`（默认 空格 / TAB / 换行，**不含**逗号冒号）。同一行还有**第二处**同机制切分：`cp $f` 的 `$f` 未加引号会**再切一次**；顺序上 word splitting 之后还会做 **pathname expansion**（名字里含 `*?[` 会被再展开，基准是**当前目录**）。改法：`for f in /data/*; do [ -e "$f" ] \|\| continue; cp -- "$f" /backup/; done` | C |
| L8 | `cat 文件 \| awk ...` 有什么问题（题目标签②：**只影响效率**） | **完全没发现**，改完的命令里仍然留着 `cat` | `awk` 自己就能读文件：`awk '{print $1}' /var/log/nginx/access.log \| ...`。`cat \|` 白多一个进程 + 一次管道数据拷贝（大日志上 IO/CPU 可观）；这种写法叫 **UUOC**（useless use of cat），**不改变结果**，所以最难被自查发现 —— 「结果对」≠「写法对」 | D |
| L9 | `uniq -c` 为什么"结果完全错"（**机制**） | "`uniq` 之前一定要做一次 `sort`，这样去重才有正确意义" —— 结论对，机制没说 | `uniq` **只比较相邻行**（man 里的 adjacent/repeated）：同一 IP 只要不连续，就会被**分别计数**，一个 IP 出现多行。`sort` 的唯一作用是把相同行**排到相邻**。更省一次排序：`awk '{c[$1]++} END{for(i in c) print c[i], i}' log \| sort -rn \| head` | C |

> **一句话记法**：`ls` 的输出是**给人眼看的文本**，不是**给程序用的列表**。要文件名列表 → glob（`/data/*`）或 `find -print0`。

### 2.2 进程、信号与退出码

| # | 题目 | 我的错答（要避免） | 正确结论 | 错因 |
|---|---|---|---|---|
| D7 | `docker stop` 后退出码是什么 | "一定是 143" | 四种结局：PID 1 装 handler 并善后 → `0`；**PID 1 未装 handler → Go 回退 `exit(2)`**；只 `Ignore`/`sh`/`sleep` 做 PID 1 → 超时 `137`；**非 PID 1** → `143` | A |
| D8 | "没装 handler → 信号被忽略"是否通用（Day 5 快问快答第 4、5 题） | 当成通用规律，据此推出 143 | 该保护**只对 PID 1 成立**（内核对 init 的保护）；非 PID 1 未装 handler 照样被杀 → 143 | C |
| D9 | `Exited (143)` 是否代表优雅关闭成功 | "是" | 判据是 **`ExitCode 0` + 日志有善后输出**；`143` 只说明"被 SIGTERM 杀死"，善后可能未发生 | C |
| D10 | `137` 的归因（Day 5 每日一题 + 变体题 B1） | 只答出"stop 超时"和"`rm -f`" | 四类来源：① PID 1 不处理 SIGTERM → `stop` 超时升级 SIGKILL ② `docker kill`（默认 SIGKILL）③ `docker rm -f` ④ 宿主层面内存挤压；区分手段：`docker events`（`kill` 带 signal、`die` 带 exitCode） + 算 `FinishedAt − StartedAt` 是否≈ `-t` | B |
| D11 | `137` 的排查顺序（Day 5 每日一题） | ① 用 137 反推顺序（循环论证）② 用 `docker logs` 找"谁杀的" ③ 用 `exec`/`stats` 查已退出容器 | ① 第 1 步要拿的是"是否 `Restarting`/`Created`" ② **SIGKILL 不可捕获**，日志只能看死前动作，"谁杀的"看 `docker events` ③ 已退出容器只能用 `logs`/`inspect`/`cp`/`diff`，进 rootfs 用 `docker run --entrypoint sh` | C |
| D12 | 查"谁杀了进程"用什么（Day 5 快问快答第 9 题） | `sysctl` | `sysctl` 是**读写内核参数**的；查信号/杀进程用 `docker events` +（VM 内）`journalctl -k \| grep -i oom` | B |
| D13 | exec 形式 CMD 写错时的排查（Day 5 快问快答第 7 题） | 想用 `docker logs` 看报错 | 该形态容器是 **`Created`**（从未运行）→ `docker logs` **为空**，唯一线索是 `State.Error`；shell 形式才有 sh 的 `not found` 日志 | D |
| D14 | `docker stats` 能否判断容器状态（Day 5 快问快答第 11 题） | "stats 能用" | 对**已退出**容器返回 `0B/0B`、`PIDS=0` 且**不报错** → 先用 `docker inspect -f '{{.State.Status}}'` 确认在跑 | D |
| D15 | `docker start e1a` 返回 1 是什么（Day 5 快问快答第 8 题） | 当成容器退出码 | 那是 **CLI 自身**的返回码；容器退出码只看 `docker inspect -f '{{.State.ExitCode}}'` | B |

### 2.3 capability 与 Docker 放宽的默认值

| # | 题目 | 我的错答（要避免） | 正确结论 | 错因 |
|---|---|---|---|---|
| D18 | **绑低端口的判定**（变体题 C1，四问错三 —— 本轮最重要） | 用传统印象"端口 < 1024 需要权限"判断 | 判定式 = **两个条件同时成立才拒绝**：`端口 < ip_unprivileged_port_start` **且** `CapEff` 无 `NET_BIND_SERVICE`；⚠️ **不写 `--sysctl` 时阈值 = Docker 给的 `0`** → 默认容器里 443 也能绑，想复现必须先 `--sysctl ip_unprivileged_port_start=1024` | A / E |
| D19 | 实验前要不要读 sysctl 基线值（Day 6 实验设计教训） | 没读就测 → 四组（root/非 root × 有/无能力）**全部成功**，结论无效 | 每组前后都 `cat /proc/sys/net/ipv4/ip_unprivileged_port_start`；**默认值会把真实判定条件掩盖** | E |
| D20 | 非 root 时 `--cap-add` 是否有效（Day 5 抽背 / Day 6） | 认为能提权 | 非 root 时 `CapPrm`/`CapEff` 被内核清空，`--cap-add` **只写入 `CapBnd`**（能力上限）→ 不生效；要真正获得能力只能 file capabilities（`setcap`）或 ambient capabilities | C |
| D21 | "容器里的 root 为什么比宿主 root 风险低"（Day 6 每日一题） | 只答了 capability 一层；措辞"uid=0 时权限位不开" | 三层：**namespace 限制可见范围** + capability 削减能力 + seccomp/AppArmor 过滤 syscall；措辞应为"**uid=0 ≠ 有能力**"；`--privileged` 不是"导致逃逸"，而是**当场取消这些限制** | C |
| D22 | `--cap-drop=ALL` 后 `ping` 仍成功说明什么（Day 6 实验 1b / 变体题 C2） | "Docker 放宽了 sysctl"（结论对，机制链说不全） | ICMP 有**两条独立路径**：raw（查 `CAP_NET_RAW`）与 datagram（查 `ping_group_range`）；`--cap-drop=ALL` 只关 raw，Docker 注入的 `ping_group_range = 0 2147483647` 仍开着；busybox `ping` 被拒后**回退**到 datagram → 仍成功。收紧要 `--sysctl net.ipv4.ping_group_range='1 0'` | D |

| D35 | `docker events --until` 的取值（Q6 **复发**） | 仍写 `--until <Finish>` | `--until` 用“现在”或更晚（`die`/`oom` 事件时间戳**晚于** `FinishedAt`）；判断“是否 stop 超时”直接算 `FinishedAt − StartedAt` 是否≈ `-t`。⚠️ 本机 dockerd 在 VM 内，`journalctl -k` 拿不到那个内核 | B |
| D36 | 查“镜像里有没有源码/密钥”的命令 | `docker exec 容器 ls -l /src` | 该写法依赖容器在跑且需知道路径；改用不依赖镜像内工具与运行状态：`docker run --rm --entrypoint find 镜像 / -name '*.go'`；查密钥：`docker inspect -f '{{json .Config.Env}}' 镜像`、`docker history --no-trunc 镜像` | B |
| D37 | `docker inspect` 的格式化语法 | `docker inspect {{.State.ExitCode}} {{.State,FinishedAt}}` | 必须带 `-f`/`--format` 且用引号：`docker inspect 名 -f '{{.State.ExitCode}} {{.State.FinishedAt}}'`（字段是 `.State.FinishedAt`，不是逗号） | B |
| D38 | `prune` 的作用范围与分寸 | “不带 -a 不会删有容器占用的卷”、“`-a` 会删即使正在跑的” | `docker system prune` **不涉及卷**（卷要 `docker volume prune`，且默认只删匿名卷）；`image prune -a` 删的是**没有任何容器（含已停止）引用**的镜像 → **运行中容器引用的镜像不会被删**。只清“停止容器 + 悬空镜像”：`docker container prune` + `docker image prune` | B / C |
| D39 | `scratch` 影响哪些 Dockerfile 指令 | “依赖 shell 的指令都不能执行”（太笼统） | 受影响的是需要 `/bin/sh -c` 的：`RUN`（构建期，故 scratch 阶段要先塞 busybox 才能再 `RUN`）、`CMD`/`ENTRYPOINT` 的 **shell form**、`HEALTHCHECK` 的 shell form | B |
