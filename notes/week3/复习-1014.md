|---|---|---|
| Docker 三大角色与启动链路 | CLI、daemon、containerd、shim、runc 各自在哪里交接？ | 通过：CLI 把请求交给 daemon，daemon 交给 containerd，containerd 启动 shim，shim 调用 OCI runtime（如 runc）创建容器进程；shim 在容器进程退出后负责回收退出码 |

| namespace 与 cgroup | 分别回答“看得见什么”与“能用多少”中的哪一类问题？ | 通过：namespace 回答「看得见什么」（PID、网络、挂载、UTS、IPC），cgroup 回答「能用多少」（CPU、内存、进程数） |

| 构建缓存 | cache key 的输入是什么？为什么这与运行期 `overlay2` 不是同一个机制？ | 部分通过：cache key 由父层 key、本层指令、本层输入内容哈希三者组成，并且与运行期 `overlay2` 无关，两条都对；缺定位命令，已记为 D43 |
| 宿主进程与容器进程 | 容器 PID 1 与宿主 PID 的关系如何证明？ | 未通过：宿主 PID 答成「不确定」、查询命令答成 `docker ps`；正确命令是 `docker inspect -f '{{.State.Pid}}'`，已记为 D40（D32 复发） |

### 1.1 篇末自测（先独立写答案）

1. 容器里的 PID 1 在宿主机上是 PID 几？用什么命令查？

5. `CapBnd` 和 `CapEff` 有什么区别？为什么 `--cap-drop=ALL` 后 setuid 二进制也提不了权？
6. 容器里的 root 逃逸之后，为什么后果不是“普通用户”而是“宿主 root”？

| 题号 | 闭卷答案要点 | 核对后的缺漏 / 错因 |
|---|---|---|
| 1 | 宿主 PID「不确定」；用 `docker ps` 看容器、用 `ps -aux` 在宿主上找进程 | 未通过（D40，D32 复发）：宿主 PID 是**确定值**，同一次运行期间不变，由 `docker inspect -f '{{.State.Pid}}' <容器>` 查询；`docker ps` 只显示容器 ID、镜像、状态、端口与名称，不含宿主 PID |
| 2 | copy-on-write；顶层建可写层，修改时把下层文件复制上来再覆盖；下层保持只读 | 通过 |
| 3 | cache key 链式比对；`COPY` 代码放在依赖安装之前会导致改一行代码就重装依赖；变更频率低的放前面 | 通过。可补精确写法：先 `COPY go.mod go.sum ./`、再 `RUN` 下载依赖、最后 `COPY . .` |
| 4 | 因 `OOMKilled` 退出，退出码 `137` | 通过。可补：137 = 128 + SIGKILL(9)；若只想限制物理内存，需要把 `--memory-swap` 与 `-m` 设成相同取值，否则默认上限是 `2 × Memory` |
| 5 | `CapBnd` 是能力上限、`CapEff` 是当前生效集合；`--cap-drop=ALL` 之后能力位被弃置，setuid 只是改 uid | 部分通过（D41）：漏掉真正的约束点 —— `CapBnd` 限制 `execve` 能获得的能力，因此 setuid 程序在 `execve` 时无法获得任何能力 |
| 6 | 容器内 uid=0 逃逸后是宿主 root；归因为「docker 用限制方式而不是隔离 uid」 | 未通过（D42）：结论对、归因错。正确机制是 Docker **默认不启用 user namespace**、没有 uid 映射；且后半段与中间自相矛盾 |

## 2. 第 2 段 · Linux 每日一题 Day 3（find）

题目取自 [Linux 每日一题](../../docs/linux/Linux-每日一题.md) Day 3。先写答案再看提示，不直接执行删除命令。

> 在 `/data` 下找出：普通文件、名字以 `.tar.gz` 结尾、修改超过 30 天、大于 50MB。① 先只打印结果不删；② 确认后再删。写出两条命令，并说明为什么 `-name` 的参数要加引号、而路径里不能带通配符。

| 要求 | 作答 |
|---|---|
| 只打印结果的命令 | `find "/data/" -type f -name "*.tar.gz" -mtime +30 -size +50M`（判定：通过） |
| 检查无误后删除的命令 | `find "/data/" -type f -name "*.tar.gz" -mtime +30 -size +50M -delete`（判定：通过；本次只在临时目录演示，未对 `/data` 执行） |
| `-name` 参数加引号的原因 | 答「阻止分词」；部分通过：实际阻止的是 **pathname expansion（glob）**，`*.tar.gz` 是字面量不触发分词；「文件含空格会出错」不成立（glob 展开的每个文件名各成一个 argv 元素）。真正的后果是：当前目录若恰好有匹配项，shell 会先把模式换成实际文件名列表 |
| `find` 的起始路径为什么写目录而非带 shell glob 的路径 | 未作答；正确机制：`find` 自行递归遍历目录树，接收的是**起始路径**；写成 `/data/*.tar.gz` 时 shell 先展开成一批文件，`find` 把每个当作**独立的起始路径**，递归范围缩成那几个文件本身；匹配为空时 `find` 报 `No such file or directory`（已记为 L10） |
| 大小单位与边界条件 | 部分通过：`M` 的方向对，但「`m` 代表字节」错 —— 字节后缀是 `c`，小写 `m` 不是合法后缀；`M` 严格说是 MiB。补充两条：`-mtime` 的数字**不带单位后缀**（`+30d` 非法）；`-mtime +30` 按 24 小时**向下取整**后比较，实际匹配至少 31 天的文件（已记为 L11） |

## 7. 十分钟速记卡

| 项目 | 内容 |
|---|---|
| 一句话主线 | Docker 负责容器镜像与运行时管理；namespace 隔离可见范围，cgroup 限制资源，镜像构建缓存与运行期存储分属不同阶段 |
| 必须记住的概念 | daemon / containerd / shim / runc；只读镜像层 / 可写层；namespace / cgroup；`CapBnd` / `CapEff`；cache key / `GOCACHE` |
| 全流程链路摘要 | CLI 请求经 daemon 与 containerd 到 OCI runtime 启动容器；构建缓存按层输入判断，容器写入进入可写层 |
| 当天实测硬结论 | 本日主线（CI 集成作业）的实测结论见 [notes/week3/day3.md](./day3.md)；复习部分得到的硬结论是：① 当 `CapBnd` 被 `--cap-drop=ALL` 清空时，setuid 程序在 `execve` 时无法获得任何能力（D41）；② 当 Docker 默认未启用 user namespace 的 uid 映射时，容器内的 uid 0 就是宿主上的 uid 0，逃逸后得到的是宿主 root（D42）；③ 当 `find` 的起始路径被 shell 先展开成文件列表时，`find` 会把这些文件当作多个起始路径，递归范围从整棵树缩成这几个文件（L10）；④ `find -size` 的字节后缀是 `c`，小写 `m` 不是合法后缀（L11） |
| 面试问答卡 | **问：Docker 缓存为什么会失效？答：构建器按层计算缓存键；当前层是否命中取决于父层结果、指令和输入内容等。上游层变化会使后续层重新构建；这与容器运行期的 `overlay2` 不是一回事。** |
| 出现异常时的排查顺序 | 先区分 build 阶段还是 run 阶段 → build 看第一处非缓存层及输入 → run 看容器状态 / 退出码 / 日志 → 再确认权限或资源限制 |
| 最容易答错 | 把 overlay2 当成构建缓存；把 Docker layer cache 当 Go 编译缓存；只看最后失败层而不找第一处缓存断点；把容器 PID 1 当宿主 PID 1 |
| 合上笔记自测 | ① `docker inspect` 如何查容器 init 的宿主 PID？② 只读层文件被修改时数据写到哪里？③ 上游 cache key 变了会影响哪些后续层？④ `needs` 会不会让 job 共享文件？ |
