### 3.2 第 4 段 · 域外口述（主域之外，来自 Docker）

> 题目取自 `docs/docker/03-Dockerfile词典.md` 篇末自测。

| Docker | Docker 03 自测第 2 题 | `CMD` 和 `ENTRYPOINT` 同时写的时候，`docker run img a b` 实际执行什么 | 未通过：只答出「执行 `ENTRYPOINT` 的指令」，未说清命令行参数与 `CMD` 的关系 | 正确口径：`docker run img a b` 实际执行的是「`ENTRYPOINT` 的指令 + `a b` 两个参数」，其中 `CMD` 被命令行参数替换掉，`ENTRYPOINT` 保持不变（例：`ENTRYPOINT ["nginx"]` 搭配 `CMD ["-g","daemon off;"]`，执行 `docker run img -T` 得到 `nginx -T`）。限定条件：该结论只在 `ENTRYPOINT` 为 exec 形式（JSON 数组）时成立；若 `ENTRYPOINT` 写成 shell 形式，则 `CMD` 与 `docker run` 的参数会被忽略；只有 `docker run --entrypoint <x>` 才会替换 `ENTRYPOINT` 本身 |

## 4. 全流程链路：一次 `apply` 到请求返回 200

> 用途：把「提交清单 → 请求到达容器」拆成两条链路记录，防止把管理关系当成数据流向。

| 阶段 | 执行者 | 输入 | 动作 | 产生的对象或状态变化 | 观察方式 |
|---|---|---|---|---|---|
| 1（控制链路） | 客户端 → API Server → etcd | 清单文件 | 校验、准入、持久化 | etcd 中出现 Deployment 对象 | `kubectl get deploy` |
| 2 | Deployment 控制器 | Deployment 的 `spec.template` | 计算 Pod 模板哈希，创建或更新 ReplicaSet | 出现 ReplicaSet 对象（`metadata.ownerReferences` 指向 Deployment） | `kubectl get rs` |
| 3 | ReplicaSet 控制器 | ReplicaSet 的 `spec.replicas` | 对账后创建 Pod 对象 | 出现 Pod 对象（此时尚未调度） | `kubectl get po` |
| 4 | 调度器 | Pod 的 `requests` 与节点可用资源 | 选择节点，写入 `spec.nodeName` | Pod 被绑定到某个节点 | `kubectl describe po` 的 Events 段落 |
| 5 | 节点上的 kubelet 与容器运行时 | Pod 的容器定义 | 拉取镜像、创建沙箱与容器 | 容器开始运行，`status` 被写回 | `kubectl get po -o wide` |
| 6（数据链路） | 客户端 → Service 的 ClusterIP | 请求 | 命中 Service，按 kube-proxy 写入的转发规则转发 | 请求到达某个就绪 Pod 的 IP 与端口 | `kubectl get endpointslices -o wide`、`curl` |

> 说明：第 1 至第 5 行属于控制链路，Deployment 与 ReplicaSet 只负责造对象、不转发任何请求；第 6 行属于数据链路，Service 与 kube-proxy 只负责转发请求、不创建任何 Pod。两条链路不能串成一条。

## 5. 结论与新确认的边界条件

> 只写「反推出的机制」「被实测推翻的说法」「新确认的限定条件」，每条写成条件句。

| 编号 | 条件句 | 依据（字段 / 命令输出） |
|---|---|---|
| 1 | 当 `spec.selector` 与 `spec.template.metadata.labels` 不匹配时，Deployment 对象在创建阶段就被 API Server 拒绝，`kubectl apply` 直接返回错误（错误信息形如 `selector does not match template labels`），而不会先创建一个空的 ReplicaSet | 被修正的说法（原先判断为「创建出空的 ReplicaSet、没有受管理的 Pod」） |
| 2 | 当 Service 省略 `spec.selector` 时，端点控制器不会创建 Endpoints 对象，必须由人创建同名的对象；因此「端点列表为空」与「端点对象不存在」是两种不同状态 | 词典 §2.4 与 §2.5 |
| 3 | 当 Service 的地址列表为空时，`kubectl get endpoints <服务名称>` 的 `ENDPOINTS` 列显示 `<none>`；未通过就绪判定的地址进入 `notReadyAddresses` 而不是 `addresses` | 词典 §2.5、现象反推第 5 条 |
| 4 | 当 Deployment 被删除时，它下面的 ReplicaSet 与 Pod 会通过 `metadata.ownerReferences` 加垃圾回收被级联删除 | 词典 §2.2 与 §2.3 |
| 5 | 在 Kubernetes v1.33 及以后，`v1` 的 Endpoints 已被标记为弃用，官方建议改用 `discovery.k8s.io/v1` 的 EndpointSlice | 命令输出 `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice` |

| 必须记住的字段 | `metadata.ownerReferences`、`status.podIP`、`status.containerStatuses[].restartCount`、`spec.selector`、`spec.template`、`spec.strategy.rollingUpdate` |
| 全流程链路摘要 | 控制链路：API Server → Deployment 控制器 → ReplicaSet 控制器 → 调度器 → kubelet；数据链路：客户端 → Service → kube-proxy → Pod |
| 本次实测得到的硬结论 | ① 执行 `kc get deploy api -o yaml` 输出 `apiVersion: apps/v1`，因此 Deployment 属于 `apps/v1`；② 执行 `kc get replicaset -o yaml` 输出 `apiVersion: apps/v1` 与 `kind: ReplicaSet`，因此 ReplicaSet 属于 `apps/v1`；③ 执行 `kc get endpoints -o yaml` 输出 `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`，因此在 v1.33 及以后应当改用 EndpointSlice |
| 出现异常时的排查顺序 | 先由字段判断结论落在哪一层（对象层 / 链路层 / 时刻），再据此选择命令 |
| 最容易答错的点 | 把容器层的重启当成 Pod 层的重建；把管理关系当成数据流向；把执行顺序当成文件可见性的条件 |
