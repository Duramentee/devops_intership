## 四、发布工作流的设计边界（取值由我填写）

> 本表列出这份工作流需要决定的每一项，以及每一项必须满足的判定条件与写错之后的后果；「我填写的取值」一列由我本人决定，再由我本人写进 `k8s_proj/.github/workflows/publish-images.yml`。

| 部分 | 这一项必须满足的判定条件与写错之后的后果 | 我填写的取值 |
|---|---|---|
| 触发事件 | 必须在「持续集成已经结束」这一个时刻获得触发机会，不能在提交被推送时就直接构建；若把构建步骤追加到 `ci.yml` 的 push 触发上，那么在持续集成尚未给出结论时镜像就已经被推送出去 | |
| 授权条件 | 必须同时约束上游工作流名称、运行结论、原始事件类型与来源分支四个条件；缺少其中任何一个，都会让发布范围扩大到「失败的运行」或者「拉取请求的运行」 | |
| 源码版本 | 必须检出被持续集成验证过的那一个提交；若使用工作流默认的检出对象，在被监控运行的提交之后 main 上又合并了新提交时，构建对象与验证对象就不再是同一个 | |
| 权限 | 只申请推送镜像与读取仓库内容这两项所需的权限；申请范围过大时，一旦工作流执行的代码不可信，损失范围会随之扩大 | |
| 凭据 | 只使用运行期间自动签发的短期凭据，并且凭据内容不能出现在命令行与日志中；写入长期凭据会使撤销与轮换变得困难 | |
| 镜像标签 | 只使用不可变的提交标识；使用 `latest` 这类浮动标签会被后续推送覆盖，从标签无法回溯到源码提交 | |
| 失败行为 | 任一构建或推送步骤失败时，整份工作流必须失败；若用回退逻辑掩盖失败，就会得到「看起来成功」的结果 | |
