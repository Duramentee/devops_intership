## 二、工作流的设计决定与理由

| 决定 | 取值 | 理由 | 写错的后果 |
|---|---|---|---|
| 触发事件 | `pull_request`（目标为 `main`）、`push`（`main`）、`workflow_dispatch` | 拉取请求阶段需要快速反馈，主分支合并之后需要确认主线自身可构建，手动触发用于复现问题 | 只写 `push` 则拉取请求阶段拿不到结果；只写 `pull_request` 则主分支被合并破坏时不会报警 |
| 权限 | `contents: read` | 这个工作流只读取源码，不需要任何写入权限；镜像发布需要 `packages: write`，那属于后续独立工作流 | 不声明则继承仓库默认权限，默认权限可能包含写入权限，一旦执行不可信代码就会扩大影响范围 |
| 并发控制 | 分组名为 `ci-<工作流名>-<引用>`，`cancel-in-progress` 为 `true` | 同一个分支上旧提交的结果已经失去意义，取消它可以缩短新提交的等待时间 | 不设置则多次高速推送会同时占用多台执行器，等待时间随推送次数线性增长 |
| 作业划分 | 拆成 `backend` 与 `frontend` 两个并行作业 | 两者技术栈与依赖完全不同，拆开之后可以独立失败、独立重跑，检查列表可以分别显示结果 | 合并成一个作业时，后端失败会导致前端检查根本不会执行，无法判断前端是否也被破坏 |
| 后端工作目录 | `defaults.run.working-directory` 取 `code/shortener/api` | 让所有 `run` 步骤默认在该目录下执行，避免在每条命令前面重复写 `cd` | 把该字段当成对所有步骤生效会写错 `uses` 步骤中的路径；`uses` 步骤的路径始终相对于仓库根目录 |
| Go 版本来源 | `go-version-file` 指向 `code/shortener/api/go.mod` | 版本由 `go.mod` 中 `go` 指令那一行决定，避免在 `go.mod` 与工作流两处各写一个版本号而出现漂移 | 两处版本不一致时，本机编译通过而持续集成失败，或者反过来 |
| 后端检查顺序 | 格式检查、编译、静态检查、单元测试 | 按照执行成本从低到高排列，成本最低的检查最先给出反馈 | 顺序颠倒时，一个格式错误要等到依赖全部下载完、测试全部跑完之后才被发现 |
| 后端测试范围 | 只运行 `internal/shortcode`、`internal/httpapi`、`internal/flusher` 三个包 | 这三个包不需要 PostgreSQL 与 Redis；需要外部服务的两个包写进来只会得到「跳过」而不是「通过」 | 把「跳过」当成「通过」，会让检查结果显示为绿色而实际上没有验证任何存储层行为 |
| 前端 Node 版本 | 写死为 `22` | 与 `web/Dockerfile` 第一阶段使用的 `node:22-alpine` 保持同一个主版本 | 两处主版本不一致时，会出现「镜像构建成功而持续集成失败」这种难以定位的差异 |
| 前端安装命令 | `npm ci --no-audit --no-fund` | `npm ci` 严格按锁文件安装，安装结果与锁文件完全一致，并且当两个文件不一致时会直接失败 | 使用 `npm install` 会在锁文件与 `package.json` 不一致时静默改写锁文件，使持续集成环境与本地环境依赖版本漂移 |
| 镜像发布 | 本工作流完全不包含 | 拉取请求阶段只需要验证权限，不需要任何软件包写入权限；两个能力由不同工作流承担 | 在拉取请求工作流里加入推送步骤，等于把发布权限交给所有提交拉取请求的人 |

## 三、需要执行的动作

> 执行顺序不能颠倒：先让工作区内容进入版本库并使检查通过，再做失败实验，最后再恢复。

### 步骤 1：把当前工作区的改动整理成提交

当前工作区已有一批未提交改动，必须先整理清楚再推送，否则持续集成检查的是远端旧代码，而不是刚写好的代码。

| 顺序 | 命令 | 说明 |
|---|---|---|
| 1 | `cd /home/drow/devops_intership/k8s_proj && git status --short` | 列出全部改动，确认每一项都属于本次要提交的范围 |
| 2 | `git add .github/workflows/ci.yml .gitignore code/shortener/web/package-lock.json` | 把工作流定义、根目录忽略规则与前端依赖锁文件加入暂存区 |
| 3 | `git add code/shortener/api/Makefile code/shortener/api/internal code/shortener/api/TASKS.md code/shortener/README.md` | 把后端与文档的既有改动加入暂存区 |
| 4 | `git commit -m "ci: add minimal backend and frontend checks"` | 单独提交持续集成相关改动，提交信息说明这个提交做了什么 |
| 5 | `git log --oneline -3` | 确认提交已经产生，并记下提交标识，后续用它追溯镜像与检查结果 |

### 步骤 2：推送并且在拉取请求上观察检查结果

| 顺序 | 命令 | 说明 |
|---|---|---|
| 1 | `git switch -c ci/minimal-workflow` | 新建一个短生命周期的分支，避免把失败实验直接提交到 `main` |
| 2 | `git push -u origin ci/minimal-workflow` | 把分支推送到远端 |
| 3 | 在浏览器中打开 `https://github.com/Duramentee/shortener_proj_k8s`，点击 `Compare & pull request` | 创建拉取请求，目标分支选择 `main` |
| 4 | 在拉取请求页面查看 `Checks` 区域 | 预期看到两个检查项：`Backend (Go)` 与 `Frontend (Vue + Vite)` |
| 5 | 展开每一个检查项，逐段阅读日志 | 观察五层结构：工作流运行、作业、步骤、每一条命令的标准输出、最终结论 |

**验收标准**：两个检查项都显示为绿色，且日志中能够看到「格式检查通过」以及 Vite 的构建产物信息。

### 步骤 3：制造一次可恢复的失败

失败实验的目的不是制造麻烦，而是证明「检查确实在执行，而不是永远返回绿色」。

| 顺序 | 操作 | 预期结果 |
|---|---|---|
| 1 | 打开 `code/shortener/api/internal/httpapi/router_test.go`，把某一个断言中的期望值改成一定不成立的取值（例如把一个期望状态码从 `200` 改成 `599`） | 本机执行 `go test ./internal/httpapi/...` 时该测试失败 |
| 2 | `git add -A && git commit -m "test: deliberately break router assertion (to be reverted)"` | 产生一个只用于验证的提交 |
| 3 | `git push` | 拉取请求上出现新的一次运行 |
| 4 | 观察检查列表 | 预期 `Backend (Go)` 变红，`Frontend (Vue + Vite)` 仍然为绿色，因为两个作业互相独立 |
| 5 | 打开 Actions 页面，选择这次运行 | 预期在该运行中只能看到 `backend` 与 `frontend` 两个作业；列表中没有名为 `publish` 或者 `push` 的作业 |
| 6 | 阅读这次运行的权限信息 | 预期只能看到读取仓库内容的权限，没有任何软件包写入权限 |
| 7 | `git revert HEAD --no-edit && git push` | 用一次反向提交恢复代码，而不是改写历史；随后检查应重新变为绿色 |

**这一步要记住的结论**：失败实验证明的是「失败的检查会让工作流变红」，而「不会走到镜像发布步骤」这件事不是靠条件判断实现的，而是因为**发布步骤根本不在这个工作流的定义里**，并且这个工作流也没有申请发布所需的权限。

| 顺序 | 命令 | 采集内容 |
|---|---|---|
| 1 | `mkdir -p /home/drow/devops_intership/code/week3/day2/outputs` | 建立本次证据的存放目录 |

> 截图之外还要在笔记里写下三个取值：工作流运行的编号、本次运行的提交标识、两条检查各自的耗时。这三个取值用来证明「同一份提交对应同一个检查结果」这条可追溯关系。

## 六、手写 `ci.yml` 的书写顺序清单

> 使用方式：按顺序从上往下写。每一行只给出「要写的键」与「书写之前必须先确定的事情」，不给出取值，取值由你自己根据判定依据决定。写完之后与模板逐行对照。

| 顺序 | 要写的键 | 书写之前必须确定的判定条件 | 可选项 |
|---|---|---|---|
| 1 | `name` | 这份工作流的名称会显示在拉取请求的检查列表与仓库的 Actions 页面上 | 任何能说明用途的字符串 |
| 2 | `on.pull_request.branches` | 拉取请求的目标分支是哪一个 | `[main]`，或者使用通配符匹配多个分支 |
| 3 | `on.push.branches` | 合并之后需要再次验证的分支是哪一个 | `[main]` |
| 4 | `on.workflow_dispatch` | 是否需要保留「人工重跑一次」这个入口 | 写入该键即启用，不写即关闭 |
| 5 | `permissions` | 这份工作流是否需要改写仓库内容或者发布软件包 | 只读取 `contents: read`；需要发布软件包时才取 `packages: write` |
| 6 | `concurrency.group` 与 `concurrency.cancel-in-progress` | 同一个分支上被取代的旧运行是否还需要继续执行 | 分组名由工作流名称与引用拼接而成，取消取 `true` |
| 7 | 作业标识与 `name` | 需要把检查拆成几个互相独立的作业，每一个作业对应哪一种技术栈 | 作业标识只能包含字母、数字、下划线与连字符，并且不能以数字开头 |
| 8 | `runs-on` | 作业运行在托管执行器上还是自托管执行器上 | 托管执行器取 `ubuntu-latest` |
| 9 | `defaults.run.working-directory` | 这个作业里的命令需要在仓库的哪个子目录下执行 | 后端取 `code/shortener/api`，前端取 `code/shortener/web` |
| 10 | 第一个步骤的 `uses` | 执行器是否需要仓库中的源码才能开始工作 | `actions/checkout@v4` |
| 11 | 工具链安装步骤 | 版本号从哪里读取，缓存的键由哪一个文件的内容决定 | `actions/setup-go@v5` 配 `go-version-file` 与 `cache-dependency-path`；`actions/setup-node@v4` 配 `node-version` 与 `cache` |
| 12 | 后端各检查步骤的排列顺序 | 哪些检查的执行成本最低，应当最先给出反馈 | 格式检查、编译、静态检查、单元测试 |
| 13 | 单元测试的包范围 | 哪些包不依赖 PostgreSQL 与 Redis | `./internal/shortcode/...`、`./internal/httpapi/...`、`./internal/flusher/...` |
| 14 | 前端依赖安装命令 | 需不需要可复现安装 | `npm ci`，或者不需要严格复现时使用 `npm install` |
| 15 | 前端生产构建命令 | 前端的生产构建入口是什么 | `npm run build` |

## 七、本日未做的事及其原因

| 未做的事 | 原因 |
|---|---|
| 不构建与推送镜像 | 镜像发布需要 `packages: write` 权限，与拉取请求阶段的最小权限原则冲突，安排在 10-15 单独建立 |
| 不接入 PostgreSQL 与 Redis 的集成测试 | 托管执行器上默认没有这两个服务，需要先确认使用服务容器或者显式启动依赖的方案，安排在 10-14 决定 |
| 不配置分支保护与必需检查 | 属于协作模型的配置，不属于工作流文件本身，安排在具备可用检查结果之后再配置 |
| 不把本机 kind 集群接入执行器 | GitHub 托管的执行器无法访问本机集群，接入本机集群需要自托管执行器，而自托管执行器会带来跨作业状态残留与私网暴露两项风险 |
