## 本周主线（一句话）

> 让应用的数据在 Pod 被重建之后依然存在，并且在应用无法启动、无法接收流量、被内核杀死这三种情况下，都能在十分钟之内依据对象的字段与事件定位到原因。

### 与第 2 周的关系

| 维度 | 第 2 周已经掌握的内容 | 第 3 周新增的内容 |
|---|---|---|
| 数据 | 容器的文件系统随容器一起消失，`ConfigMap` 与 `Secret` 以只读方式提供配置 | Pod 级的临时卷与持久卷，使数据在 Pod 被删除、重建、重新调度之后依然存在 |
| 故障 | 能够依据 `READY` 与 `RESTARTS` 两列区分「就绪失败」与「容器重启」 | 能够依据 `STATUS`、`Events`、退出码与容器状态区分「调度不上去」「镜像拉不下来」「启动即退出」「初始化容器未完成」这四类故障 |
| 资源 | 没有为容器设置任何资源字段 | `requests` 决定调度结果，`limits` 决定内核约束，两者共同决定 QoS 等级与驱逐顺序 |
| 工作负载 | 只使用 Deployment 这一种控制器 | 增加 StatefulSet 这一种控制器，它的 Pod 拥有稳定的网络标识与各自独立的存储 |

|---|---|---|

## 卡住了怎么办

| 情况 | 处理方式 |
|---|---|
| 完全没有思路 | 直接告诉我“给我一个提示”，我只提供思考方向与应当先观察的字段，不提供命令与答案 |
| 有思路但不确定 | 先把自己的预测与推导依据完整写下来再发给我，我按照“哪些地方成立、哪些地方不成立、依据是什么”逐条分析 |
| 对机制不理解 | 直接告诉我“讲一下 XX 的机制”，我按照「现象 → 机制 → 命令 → 失败模式」四个部分完整讲解 |
| 集群出现异常 | 先执行 `kubectl get po -A` 列出全部命名空间中的 Pod，确认异常范围，再执行 `kubectl describe po <名称> -n <命名空间>` 查看 `Events` 段落；如果集群已经无法恢复，最后的手段是执行 `kind delete cluster` 删除集群并重新创建，该操作会丢失节点内的全部镜像，因此需要重新执行 `kind load docker-image` 把镜像导入新节点 |
