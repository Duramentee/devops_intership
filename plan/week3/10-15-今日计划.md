## 主线执行步骤

### 1. 开工前检查

| 检查 | 目的 |
|---|---|
| `git status --short` 与相关文件 diff | 当前工作区已有未提交改动；先识别归属，避免覆盖、重置或一并提交 |
| 确认 `CI` 工作流名、事件与主分支 | `workflow_run` 过滤条件必须和真实工作流名称及默认分支一致 |
| 查看 API、Web 的 Dockerfile 与已有镜像引用 | 分别确认构建上下文、Dockerfile 路径和规范化的 GHCR 包名；不要臆测包名大小写 |

### 2. 发布工作流设计

新建独立工作流（建议路径：`k8s_proj/.github/workflows/publish-images.yml`），遵守以下边界：

| 部分 | 设计要求 |
|---|---|
| 触发 | 监听 `CI` 工作流完成事件；仅接受 `conclusion == success`、原始事件为 `push`、来源分支为 `main` 的运行 |
| 源码版本 | checkout 该次 CI 运行对应的 `head_sha`，不要 checkout 后续移动的 `main` HEAD，也不要消费来自 PR 的 artifact |
| 权限 | 发布工作流只声明所需权限；PR 检查工作流继续保持只读，不新增 `packages: write` |
| 登录 | 使用 `GITHUB_TOKEN` 登录 GHCR；不添加长期 registry token，不在命令或日志中输出 token |
| 镜像 | 分别构建 API 与 Web；使用 commit SHA 作为不可变 tag。是否额外发布 `latest` 不属于本日范围 |
| 失败行为 | 任一构建或推送失败，发布工作流应失败；不得产生成功形状的回退结果 |

> 安全验收重点：`workflow_run` 是高权限触发面，因此必须同时检查上游工作流名、成功结论、原始事件类型与 `main` 分支；不得仅因“某个 workflow 完成”就获得发布权限。

### 3. 验证顺序

1. 在本地确认两个 Dockerfile 都能以各自正确的构建上下文构建；记录镜像名称和本地构建结果。
2. 检查工作流 diff 与权限范围；若仓库已有 `actionlint`，用它检查工作流；否则做结构检查和 `git diff --check`，不为本日额外引入工具。
3. 通过 PR 验证工作流改动本身不会发布镜像；合并后等 `CI` 在 `main` 的 push 运行成功，再核对发布工作流。
4. 只有在 GHCR 中确认两个 SHA tag 均存在，并能从 tag 追溯到对应 commit 后，才将“镜像发布完成”记为通过。
5. 如今天无法合并或等待运行，则记录阻塞原因、当前验证到哪一步及下一步；不要把本地 build 记成 GHCR 发布成功。

## 复习任务细化

| 题目 | 闭卷验收点 |
|---|---|
| L7：`$(ls)` 与含空格文件名 | 命令替换输出由 shell 在未加引号时进行 word splitting；`cp $f` 还会再次分词并可能进行 pathname expansion。能说明为什么应使用 glob 或 `find -print0` 等结构 |
| L8：`cat file \| awk ...` | `awk` 可以直接读取文件；`cat` 多产生一个进程与管道拷贝，不改变结果但增加开销 |
| L9：`uniq -c` | `uniq` 只合并相邻相同行；`sort` 的作用是把相同行排到一起，不是让 `uniq` 具备全局去重能力 |
| Docker D6 | 区分 Docker 构建层缓存与 Go `GOCACHE`：分别由谁管理、缓存内容是否进入镜像层 |
| Linux Day 4：安全打印文件名 | 不使用 `for f in $(ls)`；用 glob 遍历，正确处理目录无匹配，并以 `--` 隔离以 `-` 开头的路径参数 |
| Kubernetes K25 | 闭卷复述控制链路，并把 scheduler 放在 ReplicaSet 控制器之后、kubelet 之前；说明调度结果写入 `spec.nodeName` |
| CI/CD CI2 | 区分 `needs` 的顺序依赖与 artifact 的文件传递；说明不同 job 不共享工作区文件 |
