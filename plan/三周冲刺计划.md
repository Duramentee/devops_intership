# DevOps / 云原生实习三周冲刺计划

> 计划周期：2026-10-12 至 2026-11-01  
> 目标：在不夸大 AI 辅助贡献的前提下，为短链项目补上可演示的 CI、kind 本地部署验证和基础应用可观测性；同时恢复 Docker、Linux、Shell、Kubernetes 面试表达，并于计划结束前开始投递。  
> 项目事实基线：框架、前端、Gin 路由/处理器和多数部署模板由 AI 辅助生成；本人在既有接口和实现要求下完成多数存储层方法，亲自执行训练与实验命令、观察输出、调整部分配置并验证结果。简历只写已经完成且能解释的内容。

## 一、执行原则

| 原则 | 做法 |
|---|---|
| 先预测再执行 | 每次实验或部署前，先写预期现象、验证命令和失败时的恢复办法；做完后只记录关键差异与证据。 |
| AI 作教练，不代替理解 | 先自己尝试；卡住时先索取提示，再索取示例。复制代码或 YAML 前，先用自己的话说明每个关键部分的用途。对不理解的部分不宣称掌握。 |
| 小步提交 | 每个可验证里程碑单独提交。不要为了“有提交”提交密钥、真实凭据、未验证的镜像标签或生成的大文件。 |
| 保护本地集群 | 只在确认当前 context 为个人 kind 集群后执行修改。GitHub-hosted runner 不直接连接本机 kind，不上传 kubeconfig，不为本计划配置自托管 runner 或公网 API。 |
| 用证据更新简历 | CI、镜像推送、kind 部署、指标抓取分别验收后再写入简历；没有完成的内容不提前列为技能或项目成果。 |
| 保持可持续 | 每天约 2.5–3 小时：主线实践 90–120 分钟、面试复习 30–45 分钟、笔记与整理 20–30 分钟。每周第 7 天只做轻量复盘或休息，不补做成堆任务。 |

### 每日学习资产

- 每日建立 `notes/week3/dayN.md`、`code/week3/dayN/`；后两周依次使用 `week4`、`week5`。应用代码、workflow 和 K8s 清单仍放在短链项目仓库的对应位置，学习目录只放当天的实验脚本、观察结果和复现入口。
- 每日笔记保留预测、命令、关键输出、结论和未解问题。涉及 Kubernetes 对象时按现有笔记规范维护对象词典、全流程链路和十分钟速记卡；不要重复抄对象字段表。
- 敏感值使用假值或脱敏；不把短链真实数据、密码、Secret 内容和 kubeconfig 写入公开记录。

## 三、第 1 周：CI 与本地 kind 部署闭环

**短链仓库：**[shortener_proj_k8s](https://github.com/Duramentee/shortener_proj_k8s)  
**学习材料：**`docs/github_actions_in_action/GitHub_Actions_实战薄书.md` 中 workflow、CI、artifact/image traceability、安全权限相关部分。

| 日期 | 任务 | 验收 / 当日交付 |
|---|---|---|
| 10-12 周一 | 对照短链仓库盘点 Go 测试、前端构建命令、镜像名、默认分支和现有权限；读 Actions 的 event/workflow/job/runner/step 区分。先记录 CI 需要验证的命令，不改业务代码。 | 能口头说清 push/PR 事件怎样触发 workflow，现有 Go 测试哪些需要 PostgreSQL/Redis；确认仓库没有已有 workflow 后再建。 |
| 10-13 周二 | 写最小 CI workflow：PR 与主分支 push 触发；Go 执行格式检查、build、vet 和不依赖外部服务的单元测试；前端安装依赖并运行 production build。检查 Node 依赖锁文件；如缺失，先本地生成并验证 lockfile，再用可复现安装命令。 | 新 PR 上能看到检查结果；故意制造一个可恢复的测试失败，确认 workflow 失败且不会走镜像发布步骤。 |
| 10-14 周三 | 整理 workflow 的 job 边界与缓存；若 Go 集成测试依赖 PostgreSQL/Redis，先明确哪些测试可以安全使用 Actions service container，再决定本周是否纳入，不让测试因“跳过”而伪报全绿。 | workflow 的通过条件真实覆盖已选测试；在 README 或笔记里说明未纳入的测试及原因。 |
| 10-15 周四 | 为 API 和 Web 构建镜像；在主分支成功后推送 GHCR。镜像至少带不可变的 commit SHA tag；使用 `GITHUB_TOKEN` 与最小 `packages: write` 权限，不配置长期 registry token。 | GHCR 有可拉取的两个 SHA-tagged 镜像；能从镜像 tag 追到对应 commit；PR workflow 不具备推送镜像权限。 |
| 10-16 周五 | 在学习仓库或短链项目中写本地部署/验收脚本：检查 kind context、导入指定镜像、设置 API/Web Deployment 镜像、等待 rollout，再通过 port-forward 或现有入口检查 `/api/healthz` 与 `/api/readyz`。先 dry-run/检查目标，再应用。 | 对一个指定 SHA 镜像完成 kind 本地部署验证；脚本拒绝错误 context，并在 rollout 或 HTTP 检查失败时返回非零状态。 |
| 10-17 周六 | 从 PR 检查到镜像发布再到本地 kind 验收完整走一遍；观察旧版本、新版本和失败时的状态。整理一张简短链路图和回滚方法。 | 可在 5 分钟内讲清：代码提交 → CI 测试 → 镜像构建/推送 → 本地导入 → Deployment 更新 → 健康验收；能回到上一个已知镜像版本。 |
| 10-18 周日 | 轻量复盘：口述 workflow/job/step/runner、最小权限、tag 与 commit 追溯；清理失败实验产生的资源，休息。 | 记录 3 个仍讲不清的问题；不加新功能。 |

### CI/CD 的范围边界

- 本周成果准确称为 **GitHub Actions CI + GHCR 镜像发布 + 本地 kind 部署验证**。除非部署本身也由安全、可达的 runner 自动完成，不称为“端到端自动 CD”。
- 不暴露本机集群，不在公开 PR workflow 中运行有仓库写权限的发布步骤，不把 kubeconfig、数据库密码或 Kubernetes Secret 放入 workflow 日志。
- 优先验证已存在的测试；没有测试覆盖的地方明确标记，不以“workflow 绿色”替代业务验证。

## 四、第 2 周：短链 API 基础可观测性

**学习目标：**先做应用层指标（请求量、错误、延迟），再让 Prometheus 抓取并在 Grafana 观察。日志、指标、健康检查各自回答不同问题；本周不扩展到 Loki、分布式追踪或复杂告警平台。

| 日期 | 任务 | 验收 / 当日交付 |
|---|---|---|
| 10-19 周一 | 画出浏览器/Web → API Service → API Pod → PostgreSQL/Redis 的请求链路；记录当前 healthz、readyz 和日志分别能说明什么、不能说明什么。为指标先写需求与标签设计。 | 指标草案只含低基数维度，例如 method、路由模板、状态码；不使用短码、完整 URL、用户输入或任意错误文本作为 label。 |
| 10-20 周二 | 在 AI 提示下为 API 增加 Prometheus `/metrics` 与 HTTP middleware 指标；逐段解释注册器、handler、中间件和状态码采集的作用。指标建议包括请求总数 Counter、请求耗时 Histogram；排除 `/metrics` 自抓取造成的业务计数污染。 | 本地 build/test 通过；手动发请求后 Counter 增长，Histogram 有观测值；原业务 API 响应未被指标功能破坏。 |
| 10-21 周三 | 给指标采集补最小测试；检查状态码、路由模板和异常路径；审查标签基数，确认不会记录凭据或 URL。通过第 1 周 CI 验证。 | 测试能证明请求计数与耗时采集基本正确；metrics 输出不包含短码/敏感配置。 |
| 10-22 周四 | 将新 API 镜像部署到个人 kind；从实际访问路径检查 `/metrics`；检查 API Pod、Service、EndpointSlice 与日志。部署前确认 context 和回滚镜像。 | 两个 API Pod Ready；metrics endpoint 能返回 Prometheus exposition 格式；healthz/readyz 与现有业务请求仍正常。 |
| 10-23 周五 | 在个人 kind 中部署最小 Prometheus 抓取配置，目标指向 API Service 的 `/metrics`；以 port-forward 访问 Prometheus UI 并检查 target 状态和查询结果。镜像不可拉取时按既有 kind 镜像导入流程处理。 | Prometheus target 为 UP，能查询请求 Counter 和 Histogram；记录配置、观察命令和清理/恢复方法。 |
| 10-24 周六 | 部署 Grafana 并配置 Prometheus datasource；建立精简 dashboard：请求速率、按状态码分组的请求数、延迟分位数或桶分布。使用脚本/循环请求制造可控流量，再观察面板变化。 | 面板能反映人为发出的请求和状态码变化；截图或 JSON 配置不含敏感信息；所有组件只在本地集群/port-forward 可见。 |
| 10-25 周日 | 轻量复盘：指标、日志、探针的区别；Counter 与 Histogram 的含义；为什么不能把短码当 label；演练 Prometheus target DOWN 时先查什么。 | 写一页观测链路与故障排查顺序；删除临时压力请求或恢复服务基线，休息。 |

### 可观测性深度边界

- 首版只覆盖应用指标和本地仪表盘，不承诺生产级告警、长期存储、高可用或容量规划。
- 不为得到好看的曲线伪造性能提升结论；没有规范压测与重复测量，就不写吞吐量、延迟优化百分比。
- 若本地资源或镜像网络成为阻塞，优先完成 `/metrics`、Prometheus target UP 和一张有效 dashboard；Grafana 可延后，不把堆组件当成完成度。

## 五、第 3 周：面试复习、讲述和投递

每天采用“闭卷口述 → 实际命令/小实验 → 查错补缺”的方式。先说不知道的部分，不靠背长段笔记掩盖空白。复习入口优先使用 [错题本](../notes/错题本.md)、[Kubernetes 反例与关系](../notes/week2/提炼-反例与关系.md)、[Kubernetes 排障速查](../notes/k8s-排障速查.md)、[Docker 词典](../docs/docker/01-架构与原理.md)、[Linux 故障索引](../docs/linux/Linux-故障索引.md)。

|---|---|---|
| 10-26 周一 | Linux：进程与信号、CPU/内存/磁盘、网络连通性、日志定位。做 3 道现象题，至少亲自运行一组 `ps`/`free`/`df`/`du`/`ss`/`lsof` 相关命令。 | 能按“现象 → 假设 → 命令 → 输出含义”回答 3 题；投递第一批 1–2 个匹配岗位，不等计划结束。 |
| 10-27 周二 | Shell：引号、IFS 分词、glob、管道、`grep`/`awk`、退出码、`set -euo pipefail` 的边界。手写一个安全处理文件列表的小脚本。 | 脚本能处理空格文件名和空匹配；能解释为什么 `for f in $(ls)` 不可靠。 |

| 10-29 周四 | Kubernetes 基础：Pod/Deployment/ReplicaSet、Service selector 与 EndpointSlice、ConfigMap/Secret、探针、资源请求限制。抽取短链项目 selector 故障演练做 90 秒复盘。 | 能讲清 API 502 → Pod Ready → selector/label 不匹配 → EndpointSlice 无端点 → 最小修复与验收；说明记录证据边界。 |
| 10-30 周五 | Kubernetes 发布 + CI/CD + 可观测性：解释滚动升级、readiness、失败升级时旧副本行为；讲清 Actions 工作流权限、GHCR tag 追溯、Prometheus 指标链路。 | 完成一次 20–30 分钟模拟面试；把答不清的问题记入错题本；投递第二批 1–2 个岗位。 |
| 10-31 周六 | 项目讲述与简历校验：逐条核对“我亲自做的 / AI 提供的 / 我能解释的 / 还在补的”；检查链接、日期、镜像数值与公开仓库描述。 | 形成 2 分钟短链项目介绍、1 分钟 Docker 实验介绍；不把未完成的 CD/监控能力写成已掌握。 |
| 11-01 周日 | 最终轻量复测与下一周期安排。重跑最关键的一次 CI、一次 kind 健康验证、一次指标查询；投递或补充至少 1 个岗位，并列出后续两周学习重点。 | 简历与仓库事实一致；至少开始投递；保留一份具体的面试薄弱点清单。 |

## 六、面试复习轮换清单

| 方向 | 优先掌握的 5 个问题 |
|---|---|
| Linux | 如何区分 CPU 忙、内存不足、磁盘空间不足和 inode 耗尽？删除文件后空间未释放怎么查？服务端口不通如何分层验证？僵尸进程是什么？日志如何安全地统计/筛选？ |
| Shell | 未加引号的变量展开会发生什么？`uniq` 为什么常要先排序？如何安全遍历包含空格的文件名？管道中间命令失败时怎样发现？脚本如何处理参数和错误？ |
| Docker | 镜像层与容器可写层是什么？Dockerfile 指令顺序如何影响缓存？多阶段构建解决什么问题？容器退出 137/143 各可能意味着什么？volume 与 bind mount 如何选择？ |
| Kubernetes | Deployment 到 Pod 的控制关系是什么？Service 怎样找到 Pod？Ready 与 Running 有何区别？Readiness 与 Liveness 各影响什么？`ImagePullBackOff`、`CrashLoopBackOff`、`CreateContainerConfigError` 如何分辨？ |
| CI/CD | Event、workflow、job、step、runner 的关系是什么？PR 检查和发布 job 如何隔离权限？镜像如何追溯到 commit？为什么本机 kind 不该暴露给 hosted runner？本项目实际做到哪一段交付？ |
