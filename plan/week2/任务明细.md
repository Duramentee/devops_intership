## 本周主线（一句话）

> 把第 1 周已经容器化的 **webapp 镜像**部署到 Kubernetes 集群：第一步创建最基础的 Pod 对象，第二步为这个 Pod 配置存活探针（让容器进程异常时能够自动重启）与副本控制器（让 Pod 数量始终等于期望值）。

### 与第 1 周的关键切换（先建立心理模型）

| 维度 | Docker（第 1 周） | Kubernetes（第 2 周） |
|---|---|---|
| 运行单位 | 容器（container） | Pod，也就是一组一起运行、且始终位于同一节点上的容器 |
| 镜像从哪里来 | 宿主机上 Docker 守护进程镜像库中已有的镜像可以直接使用 | 只能使用节点内部容器运行时镜像库中的镜像，因此必须先把镜像导入节点（执行 `kind load docker-image`） |
| 网络如何访问 | 通过宿主机上的 DNAT 规则把端口映射进容器，也就是 `-p 8080:8080` | 每个 Pod 都拥有独立的 IP 地址；调试时使用 `kubectl port-forward`，正式的对外暴露方式要在第 3 周学习 Service 时介绍 |
| 进程退出之后怎么办 | 需要自己执行 `docker start` 来重启容器 | 由 kubelet 根据存活探针（livenessProbe）的结果自动重启容器 |
| 容器被删除之后怎么办 | 容器对象消失，不会自动恢复 | 由副本控制器（ReplicaSet 或 Deployment）自动创建一个新的 Pod 来补齐数量 |
| 由谁执行管理动作 | 由人手动执行命令 | 由运行在节点上的 kubelet 与运行在控制平面上的控制器共同执行，其行为模式是声明式的状态对账 |

## Day 1 · 第一部分：Pod（把容器交给 Kubernetes 调度）

| 项 | 内容 |
|---|---|
| 目标 | 从机制上理解 Pod 对象的定义与行为，并在 Kubernetes 集群中成功运行第一个工作负载 |
| **机制** | Pod 是一组被放在同一个节点上共同运行的容器集合，它是 Kubernetes 执行调度的最小单位，因此同一个 Pod 内部的多个容器永远位于同一个节点上，不可能被拆分到两个节点。同一个 Pod 内部的容器共享 Network、UTS、IPC 这三种命名空间，所以它们共用同一个 IP 地址、同一个主机名与同一个端口空间，彼此之间通过 `localhost` 就能通信；而它们的文件系统默认是隔离的，除非我们显式地挂载共享卷。由此可以推出三个结论：① 同一个 Pod 内部的两个容器不能监听同一个端口，因为它们的端口空间是共用的；② 不同 Pod 的端口空间彼此独立，因此永远不会发生端口冲突；③ Pod 是一次性对象，删除它等价于新建一个全新的 Pod（会得到新的名称与新的 IP 地址），只有容器这一层会被重启（表现为 `RESTARTS` 列的计数增加），因此“Pod 被重启”这种说法是不正确的。 |
| 任务 | ① 检查集群状态：先执行 `docker ps -a --filter name=kind` 查看 kind 节点容器的状态，再执行 `kubectl get nodes` 确认每一个节点都处于 `Ready` 状态；如果节点容器处于 `Exited` 状态，则先执行 `docker start kind-control-plane` 把它启动起来。② 把镜像导入节点：执行 `kind load docker-image webapp:v4`，把宿主 Docker 中的镜像写入 kind 节点内部的容器镜像库，因为节点上的 kubelet 只能看到节点自己镜像库中的镜像。③ 生成 YAML 模板（只输出到文件、不创建任何资源）：执行 `kubectl run webapp --image=webapp:v4 --port=8080 --dry-run=client -o yaml > /tmp/pod.draft.yaml`，然后逐字段阅读这份模板，分清哪些字段是必填项、哪些字段是由 Kubernetes 自动补全的默认值。④ **自己写** `code/week2/day1/pod.webapp.yaml`，并在其中增加 `app=webapp` 与 `env=dev` 两个标签。⑤ 创建资源并观察：依次执行 `kubectl create -f`、`kubectl get po -o wide`、`kubectl describe po webapp`、`kubectl logs webapp`。⑥ 转发端口并验证访问：执行 `kubectl port-forward po/webapp 8888:8080`，然后在另一个终端窗口中执行 `curl localhost:8888`。⑦ 进入容器内部：执行 `kubectl exec -it webapp -- sh`，在容器内分别查看 `/proc/1/cmdline`、`hostname`、`env` 三个文件或命令的输出。⑧ 删除并重建：执行 `kubectl delete po webapp`，随后重新执行 `kubectl create -f`，**对比重建前后的 Pod IP 与 Pod 名称是否发生变化**。 |
| **面试问答卡** | ① 同一个 Pod 内部的两个容器共享哪些命名空间？它们的文件系统是共享的吗？它们能监听同一个端口吗？② `RESTARTS` 这一列统计的是什么？“Pod 重启”这种说法错在哪里？③ 为什么在宿主机上执行 `docker images` 能够看到的镜像，kind 集群的节点却看不到？④ Docker 的 `-p 8080:8080` 与 Kubernetes 的 `port-forward` 在实现机制上有什么本质区别？ |
| 自检 | 能够说清 Pod 与容器之间的三层关系（Pod 中包含容器、Pod 是调度单位、同一个 Pod 内的容器共享哪些命名空间）；能够解释 `kubectl describe` 输出末尾 Events 段落中每一行的含义。 |
| 笔记落点 | `notes/week2/day1.md` 新增「Pod 与容器的关系」以及「集群是如何把镜像变成运行中容器的」。 |

### Day 1 · 第二部分：Deployment（把 Pod 交给控制器管理）

| 项 | 内容 |
|---|---|
| 目标 | 理解 Deployment、ReplicaSet、Pod 三层对象之间的管理关系，并使用 Deployment 完成一次可自愈的部署 |
| **系统机制（本周保留项）** | Deployment 并不直接创建容器，它管理的是 ReplicaSet，而 ReplicaSet 管理的是 Pod，Pod 内部才是容器，因此从提交到运行一共存在四层对象：Deployment → ReplicaSet → Pod → 容器。这个层次结构解释了三件事：第一，Deployment 之所以能够记录版本历史，是因为它在升级时保留旧的 ReplicaSet；第二，副本数量由 ReplicaSet 持续对账维持，而不是由 Deployment 直接维持；第三，Pod 的名称中带有随机后缀，原因是这些 Pod 由控制器创建，每次创建都会生成新的名称。与第一部分创建的裸 Pod 相比，由 Deployment 管理的 Pod 在被删除之后会被自动补齐，这就是本周要掌握的第一个“自愈”行为。 |
| 任务 | ① 编写 `code/week2/day1/deploy.webapp.yaml`，其中把 `replicas` 设置为 2，并且让 `selector.matchLabels` 与 Pod 模板中的标签保持一致，然后执行 `kubectl apply -f` 创建它。② 执行 `kubectl get deploy,rs,po`，在一条命令的输出中同时观察三层对象，并且找出两个 Pod 名称的共同前缀。③ 执行 `kubectl delete po <其中一个 Pod 的名称>`，然后执行 `kubectl get po -w` 观察控制器自动创建新 Pod 的过程，记录新旧 Pod 的名称与 IP 地址。④ 执行 `kubectl scale deploy webapp --replicas=4`，确认 Pod 数量被调整为 4；再执行 `kubectl scale deploy webapp --replicas=2`，确认多余的 Pod 被删除。⑤ 执行 `kubectl port-forward deploy/webapp 8888:8080`，在另一个终端执行 `curl localhost:8888`，确认通过 Deployment 的名称也能够转发端口。⑥ 把裸 Pod 与 Deployment 的差异整理成一张对照表写入笔记。 |
| **面试问答卡** | 问：Deployment、ReplicaSet、Pod 三者是什么关系？答：Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod，Pod 内部才是容器。问：Deployment 为什么能够回滚？答：因为升级时它会保留旧的 ReplicaSet，回滚时把旧 ReplicaSet 的副本数量重新调大即可。问：删除一个由 Deployment 管理的 Pod 之后会发生什么？答：ReplicaSet 控制器在下一轮对账中发现实际副本数量少于期望副本数量，因此创建一个新的 Pod 来补齐，新 Pod 的名称与 IP 地址都与被删除的那个不同。问：裸 Pod 与 Deployment 管理的 Pod 有什么差别？答：裸 Pod 删除之后不会自动恢复，也无法滚动升级；由 Deployment 管理的 Pod 删除之后会被自动补齐，并且能够升级与回滚。 |
| 自检 | 能够画出 Deployment → ReplicaSet → Pod → 容器四层结构，并且能够说明每一层分别负责什么。 |
| 笔记落点 | `notes/week2/day1.md` 新增「Deployment 与 ReplicaSet 的关系」以及「裸 Pod 与 Deployment 的差异对照表」。 |

## Day 2 · Service 与标签选择器

| 项 | 内容 |
|---|---|
| 目标 | 让应用拥有一个稳定的访问入口，并理解 Service 是通过什么机制找到 Pod 的 |
| **系统机制（本周保留项）** | Pod 的 IP 地址是不稳定的，因为 Pod 重建之后会得到新的 IP，所以不能把 Pod 的 IP 写进客户端配置。Service 解决这个问题的方式是提供一层稳定的虚拟地址：Service 对象本身没有进程，也不监听端口，真正完成转发的是每个节点上的 kube-proxy，它依据 Service 对象与 Endpoints 对象在节点上写入转发规则。Service 通过标签选择器持续筛选符合条件并且处于就绪状态的 Pod，把它们的地址写入 Endpoints 对象（新版本中为 EndpointSlice），因此 Pod 的 IP 变化只会导致 Endpoints 内容更新，客户端访问的地址保持不变。三种类型的区别是：ClusterIP 只在集群内部可以访问；NodePort 会在每个节点上开放一个固定的端口，因此可以从集群外部访问；LoadBalancer 会向云平台申请一个外部负载均衡器，kind 集群不支持这种类型，只做概念了解。 |
| 任务 | ① 编写 `code/week2/day2/svc-clusterip.yaml`，类型设置为 ClusterIP，选择器指向 Day 1 中使用的标签。② 执行 `kubectl create -f` 创建它，然后执行 `kubectl get svc` 与 `kubectl get endpoints <服务名称>`，确认端点列表中包含了全部处于就绪状态的 Pod 地址。③ 在集群内部验证访问：执行 `kubectl run tmp --image=busybox:1.36 --rm -it --restart=Never -- wget -qO- http://<服务名称>:8080`，观察返回内容。④ 执行 `kubectl delete po <其中一个 Pod 的名称>`，待新 Pod 创建完成后再次执行 `kubectl get endpoints <服务名称>`，对比端点列表的变化。⑤ 执行 `kubectl edit svc <服务名称>`，把选择器改成不匹配任何 Pod 的取值，然后观察端点列表的变化以及访问请求的结果。⑥ 编写 `code/week2/day2/svc-nodeport.yaml`，类型设置为 NodePort，执行 `kubectl get svc` 查看系统分配的节点端口，然后在宿主机上执行 `curl localhost:<节点端口>`。⑦ 把三种类型的区别整理成表格写入笔记。 |
| **面试问答卡** | 问：Service 是通过什么机制找到 Pod 的？答：Service 通过标签选择器筛选 Pod，把符合条件并且处于就绪状态的 Pod 地址写入 Endpoints 对象，kube-proxy 依据这些信息在节点上配置转发规则。问：Pod 的 IP 地址变化之后为什么不会影响客户端访问？答：因为客户端访问的是 Service 的固定地址，Pod 的 IP 变化只会导致 Endpoints 对象的内容更新。问：ClusterIP 与 NodePort 有什么区别？答：ClusterIP 只能在集群内部访问，NodePort 会在每个节点上开放一个固定端口，因此可以从集群外部访问。问：Service 到 Pod 的转发由哪个组件完成？答：由每个节点上的 kube-proxy 配置转发规则来完成，Service 对象本身没有进程，也不监听端口。 |
| 自检 | 能够按照「客户端 → Service → Endpoints → Pod」的顺序，说明链路上每一步由哪个组件负责。 |
| 笔记落点 | `notes/week2/day2.md` 新增「Service 与 Endpoints 的关系」以及三种类型对照表。 |

## Day 3 · ConfigMap 与 Secret（把配置从镜像中分离）

| 项 | 内容 |
|---|---|
| 目标 | 把配置从镜像中分离出来，并理解 Secret 与 ConfigMap 的差别与边界 |
| **系统机制（本周保留项）** | 镜像里应当只包含程序本身，配置应当在部署时注入，理由有两点：第一，同一份镜像需要能够部署到开发、测试、生产三个环境；第二，修改配置时不应该重新构建镜像。Kubernetes 提供两种配置对象：ConfigMap 用于存放普通配置，Secret 用于存放敏感信息，两者在注入方式上完全相同。注入方式有两种：第一种是以环境变量注入，由 kubelet 在创建容器时把取值写入进程环境，因此容器启动之后再修改配置不会影响已经运行的容器；第二种是以文件形式挂载，由 kubelet 把内容写入卷再挂载到容器内的目录，因此修改配置之后容器内的文件会在一定延迟后同步更新。需要特别说明的是：Secret 只做 base64 编码，并不做加密，它的安全性依靠访问控制（RBAC）与传输加密来保证，因此不要把 Secret 文件提交到代码仓库。 |
| 任务 | ① 修改应用，让它从环境变量中读取一个配置项（例如问候语或监听端口），重新构建镜像并执行 `kind load docker-image` 导入节点。② 编写 `code/week2/day3/cm.yaml` 与 `code/week2/day3/secret.yaml`，前者存放一个普通配置项，后者存放一个敏感配置项。③ 在 Deployment 中使用 `envFrom` 或 `valueFrom` 引用这两个对象，创建之后执行 `kubectl exec -it <Pod 名称> -- env`，确认环境变量已经注入。④ 改用卷挂载的方式再注入一次，确认容器内出现了对应的文件，并用 `cat` 查看文件内容。⑤ 执行 `kubectl edit cm <名称>` 修改配置，分别观察环境变量方式与卷挂载方式下的容器行为差异。⑥ 依次执行 `kubectl describe cm`、`kubectl describe secret` 与 `kubectl get secret <名称> -o yaml`，确认 Secret 与 ConfigMap 的存储形式，并验证 Secret 存放的是 base64 编码而不是明文，也不是密文。 |
| **面试问答卡** | 问：为什么要把配置放在 ConfigMap 中，而不是写进镜像？答：因为同一份镜像需要部署到多个环境，而且修改配置时不应该重新构建镜像。问：以环境变量注入与以卷挂载注入有什么区别？答：环境变量在容器创建时写入进程环境，修改配置后需要重启容器才能生效；卷挂载写入文件，修改配置后文件会在一定延迟后自动更新。问：Secret 是加密存储的吗？答：不是，它只做 base64 编码，安全性依靠访问控制与传输加密来保证。问：Secret 与 ConfigMap 在用法上有什么区别？答：两者的注入方式相同，区别在于用途与访问控制，Secret 用于敏感信息，并且可以被单独授权。 |
| 自检 | 能够说明一次配置变更在环境变量方式与卷挂载方式下，分别需要做什么操作才能生效。 |
| 笔记落点 | `notes/week2/day3.md` 新增「配置注入两种方式的差异」对照表。 |

## Day 4 · 存活探针与就绪探针（让应用具备自愈能力）

| 项 | 内容 |
|---|---|
| 目标 | 让应用具备自动重启与自动摘除流量的能力，并能够区分两种探针的不同后果 |
| **系统机制（本周保留项）** | 两种探针回答的是两个不同的问题。存活探针回答“这个容器还需要继续运行吗”，检查失败时 kubelet 会重启容器，也就是杀掉容器内的主进程并重新启动它，重启发生在同一个 Pod 内部，因此 Pod 的名称与 IP 地址都不改变，只有 `RESTARTS` 这一列的计数增加。就绪探针回答“这个 Pod 现在可以接收流量吗”，检查失败时 kubelet 不会重启容器，而是把该 Pod 从 Service 的 Endpoints 列表中移除，使流量不再被转发到这个 Pod。执行检查动作的是 Pod 所在节点上的 kubelet，而不是控制平面，它支持三种检查机制：HTTP GET（当返回的状态码属于 2xx 或 3xx 时判定为成功）、TCP socket（当能够建立 TCP 连接时判定为成功）、exec（当容器内执行的命令返回退出码 0 时判定为成功）。对于启动速度较慢的应用，应当使用启动探针，在启动探针成功之前，存活探针与就绪探针都不会开始执行。 |
| 任务 | ① 为应用增加 `/healthz` 与 `/readyz` 两个端点，其中 `/healthz` 先返回状态码 500，用于人为制造存活探针失败，`/readyz` 先返回状态码 200。② 重新构建镜像并导入节点，版本标记为 `webapp:v5`。③ 编写带 `livenessProbe` 的 Deployment，把 `initialDelaySeconds` 设置为 5，执行 `kubectl get po -w` 观察 `RESTARTS` 的增长，并用 `kubectl describe po` 查看 `Liveness probe failed` 与 `Killing container` 两类事件。④ 把 `/healthz` 的返回值改回 200，重新构建并导入镜像，确认容器不再被重启。⑤ 编写同时带两种探针的 Deployment，把 `/readyz` 改为返回 500，观察 `READY` 列变为 `0/1` 而 `RESTARTS` 列保持为 `0`，并执行 `kubectl get endpoints <服务名称>` 确认该 Pod 已经离开端点列表。⑥ 把 `initialDelaySeconds` 调整为过小的取值，观察应用刚启动就被杀掉的循环，并记录此时容器的退出码。⑦ 执行 `kubectl logs --previous` 查看上一个被终止的容器的日志。 |
| **面试问答卡** | 问：存活探针与就绪探针有什么区别？答：存活探针失败时会重启容器，就绪探针失败时会把 Pod 从 Service 的端点列表中移除，不会重启容器。问：探针的检查动作由哪个组件执行？答：由 Pod 所在节点上的 kubelet 执行，而不是由控制平面执行。问：`initialDelaySeconds` 设置得过小会怎样？答：应用还没有启动完成就被判定为检查失败，kubelet 会反复重启容器，容器会陷入重启循环。问：健康检查端点为什么不能要求身份认证？答：因为探针请求不会携带认证信息，如果端点要求认证，检查会永远失败，容器会被反复重启。 |
| 自检 | 能够仅凭 `READY` 与 `RESTARTS` 两列的取值，判断出当前是“不健康但未重启”还是“正在反复重启”。 |
| 笔记落点 | `notes/week2/day4.md` 新增「三种探针决策表」以及实测输出逐字段解析。 |

## Day 5 · 滚动升级与回滚（不中断服务地发布新版本）

| 项 | 内容 |
|---|---|
| 目标 | 完成一次不中断服务的升级，并且能够用一条命令回滚到上一个版本 |
| **系统机制（本周保留项）** | Deployment 的升级过程是：新建一个 ReplicaSet，逐步扩大新 ReplicaSet 的副本数量，同时逐步缩小旧 ReplicaSet 的副本数量，直到新 ReplicaSet 的副本数量等于期望值。控制这个过程的是两个参数：`maxSurge` 决定在期望副本数量之外最多可以多创建多少个 Pod，`maxUnavailable` 决定升级过程中最多允许多少个 Pod 处于不可用状态，两者共同决定了升级期间实际运行的 Pod 数量下限与上限。Deployment 保留旧的 ReplicaSet，是为了提供回滚能力：执行回滚时，控制器把旧 ReplicaSet 的副本数量重新调大，把新 ReplicaSet 的副本数量调小。另外，触发升级的方式有两种：修改 Pod 模板（例如更换镜像标签）会触发滚动升级并且创建新的 ReplicaSet；只修改副本数量这类字段则不会创建新的 ReplicaSet。 |
| 任务 | ① 执行 `kubectl get deploy webapp -o yaml`，找到 `strategy` 字段，记录两个参数的默认取值。② 修改 Deployment 中的镜像标签（从 `webapp:v4` 改为 `webapp:v5`），执行 `kubectl apply -f`，然后执行 `kubectl rollout status deploy/webapp` 观察升级过程，并执行 `kubectl get rs` 观察新旧两个 ReplicaSet 的副本数量变化。③ 执行 `kubectl rollout history deploy/webapp` 查看版本历史，再执行 `kubectl rollout undo deploy/webapp` 回滚，并用 `kubectl describe deploy webapp` 确认当前使用的镜像标签已经回到上一个版本。④ 把 `maxSurge` 与 `maxUnavailable` 分别设置为不同的组合，观察升级过程中 Pod 总数的变化，并记录每一次观察到的数量。⑤ 制造一次失败的升级：把镜像标签改成一个不存在的版本，执行 `kubectl rollout status` 观察它的处理方式，然后执行回滚恢复。 |
| **面试问答卡** | 问：Deployment 的滚动升级过程是怎样的？答：控制器创建一个新的 ReplicaSet，逐步增加它的副本数量，同时逐步减少旧 ReplicaSet 的副本数量，直到新 ReplicaSet 的副本数量等于期望值。问：`maxSurge` 与 `maxUnavailable` 分别控制什么？答：`maxSurge` 控制在期望副本数量之外最多可以多创建多少个 Pod，`maxUnavailable` 控制升级期间最多允许多少个 Pod 不可用。问：回滚是如何实现的？答：因为 Deployment 保留了旧的 ReplicaSet，回滚时把旧 ReplicaSet 的副本数量调大，把新 ReplicaSet 的副本数量调小。问：升级过程中如果新版本的镜像拉取失败会怎样？答：新的 Pod 无法进入就绪状态，升级过程会停滞，此时可以执行回滚恢复到上一个可用版本。 |
| 自检 | 能够解释一次升级过程中 `kubectl get rs` 输出的副本数量为什么会先增加后减少，以及这种变化与两个参数之间的关系。 |
| 笔记落点 | `notes/week2/day5.md` 新增「滚动升级过程记录」以及「升级与回滚命令表」。 |
