## Day 1 · 容器到底是什么

| 项 | 内容 |
|---|---|
| 目标 | 从机制上理解容器；跑通第一个容器 |
| **机制** | 容器 ≠ 轻量虚拟机。**容器 = 一组 namespace（隔离视图）+ cgroup（限制资源）的普通 Linux 进程**，与宿主机**共用同一个内核**。推论：① 容器里的进程在宿主机 `ps` 里**看得见** ② "启动快"是因为没有内核要启动，不是玄学 ③ 容器里的 PID 1 在宿主机上另有 PID |
| 任务 | ① 读 `docs/k8s_in_action/01-容器与K8s入门.md` 的「容器 vs 虚拟机」② `docker run --rm hello-world` ③ `docker run -d --name t1 alpine sleep 300` ④ 在宿主机 `ps -ef \| grep sleep` 找到它 ⑤ `docker exec t1 ps aux` 对比两侧 PID ⑥ `docker rm -f t1` 后确认宿主进程也没了 |
| **每日一题**（现象题） | 容器里的 `sleep 300`，为什么在宿主机 `ps` 里能看到？如果容器真是"轻量虚拟机"，还会看到吗？再答：容器里的 PID 1 在宿主机上的 PID 是多少，用什么命令查？ |
| 自检 | 能说出至少 4 种 namespace（pid / net / mnt / uts / ipc / user）和 cgroup 各管什么 |
| 笔记落点 | `notes/week1/day1.md` 新增一节「容器 vs 虚拟机（机制）」 |

## Day 2 · 镜像分层与 Dockerfile

| 项 | 内容 |
|---|---|
| 目标 | 亲手写出第一个 Dockerfile，并理解"分层 + 缓存" |
| **机制** | 镜像 = 一堆**只读层**叠起来（overlay2）；**每条 Dockerfile 指令生成一层**；容器启动时在最上面加一个**可写层**（写时复制 Copy-on-Write）。三个推论：① 相同层可复用 → 拉取/构建快 ② **改一行代码只重建它之后的所有层** → 指令顺序决定缓存命中率 ③ 容器里改文件走 copy-up，改的永远是可写层 |
| 任务 | ① 用 `labs/实践任务.md` 第五部分那个 Go 服务（`main.go`）② **自己先写 Dockerfile**（写完再找我）③ `docker build -t webapp:v1 .` ④ `docker run -p 8080:8080 webapp:v1` + `curl localhost:8080` ⑤ `docker history webapp:v1` 看每层大小 ⑥ 改一行代码再 build，观察输出里的 `CACHED` |
| **每日一题**（顺序题） | 这个顺序为什么每次改代码都要重装依赖？该怎么调？`FROM golang` → `COPY . .` → `RUN go mod download` → `RUN go build -o app .` |
| 自检 | 能解释"为什么 `COPY go.mod go.sum ./` 要单独一层、放在 `COPY . .` 之前" |

## Day 3 · 多阶段构建：把镜像压小

| 项 | 内容 |
|---|---|
| 目标 | 用多阶段构建产出小镜像 |
| **机制** | 多阶段 = 多个 `FROM`，用 `COPY --from=<stage>` 从构建阶段**只捞产物**过去，builder 阶段的内容**不会**进最终镜像。Go 是静态编译 → 运行阶段只放一个二进制；极致可以放 `scratch`（空镜像）或 `distroless`。相关开关：`CGO_ENABLED=0`（不依赖 libc）、`-ldflags "-s -w"`（去符号表） |
| 任务 | ① 先记下单阶段镜像大小 ② 改多阶段，再记一次（`docker images`）③ 试 `scratch` / `distroless` ④ `docker history` 前后对比写进笔记 |
| **每日一题**（命令题） | ① 一条命令看"镜像每层多大"？② 一条命令看"运行中容器的资源占用"？③ `scratch` 镜像里**没有 shell**，这对排障意味着什么、怎么补救？ |
| 自检 | 能说清"builder 阶段为什么不会被打包进最终镜像" |

## Day 4 · 数据与网络

| 项 | 内容 |
|---|---|
| 目标 | 搞清"容器数据为什么丢"和"端口为什么通/不通" |
| **机制** | 可写层随容器删除而消失 → 要持久化必须用 **volume**（Docker 管理）或 **bind mount**（宿主目录）。网络：默认 bridge + NAT，`-p 8080:80` 本质是宿主机上的 DNAT 规则；**自定义网络**里容器可以用**容器名互相解析**（Docker 内嵌 DNS），默认 bridge 不行 |
| 任务 | ① 容器内写文件 → `docker rm -f` → 重建，确认数据没了 ② 加 `-v webvol:/data` 重做，确认数据还在 ③ bind mount 一个宿主目录对比 ④ `docker network create mynet` 起两个容器，用名字互相 ping |
| **每日一题**（排障题） | 现象："重启容器后应用配置全丢。" 写出至少 3 个可能原因，以及每个原因的**验证命令**。（提示：可写层 / volume 挂错路径 / 配置在构建时就写进镜像了） |
| 自检 | 能说清 `-v webvol:/data` 与 `-v /host/dir:/data` 的区别，以及 `--rm` 对两者的影响 |

## Day 5 · 排障工具链 + 故意制造故障

| 项 | 内容 |
|---|---|
| 目标 | 形成"容器出问题先看什么"的条件反射 |
| **机制** | 排障是**分层定位**：① 容器在不在（`docker ps -a`）② 进程为什么停（`docker inspect` → `State.ExitCode`）③ 输出说了什么（`logs`）④ 环境对不对（`exec` 进去看）⑤ 资源够不够（`stats`）。**退出码速记**：`0` 进程正常结束（对服务型进程反而异常）、`1` 应用报错、`137` 被 SIGKILL（常见 OOM）、`143` 收到 SIGTERM（优雅停止） |
| 任务 | ① 故意把 `CMD` 写错（指向不存在的文件）→ build → run → 用退出码判断原因 ② 起一个立刻退出的容器，用 `logs` 找原因 ③ `docker stats` 看资源 ④ `docker system df` 看磁盘占用 + `docker system prune` 清理 |
| **每日一题**（排障题） | 容器 `Exited (137)`。写出排查顺序（≥4 步），并回答：137 与 143 的区别是什么？为什么这个区别对"优雅关闭"很关键？ |
| 自检 | 能读懂 `docker inspect` 里的 `State.ExitCode`、`State.OOMKilled`、`State.FinishedAt` |

## Day 6 · 容器安全 + Dockerfile 收尾

| 项 | 内容 |
|---|---|
| 目标 | 把 Dockerfile 做成"能拿去面试"的版本 |
| **机制** | 容器默认以 **root** 运行，并默认带一批 capability。容器里的 root 与宿主 root 差一个 namespace + capability，但**一旦逃逸就等于宿主 root**。所以：非 root 运行、丢 capability、只读根文件系统、绝不把密钥烤进镜像 |
| 任务 | ① 加 `USER`（非 root）、`.dockerignore`、`HEALTHCHECK` ② `docker run --cap-drop=ALL` 跑一遍 ③ 检查镜像里有没有混入 go 工具链 / 源码 / 密钥 |
| **每日一题**（概念题） | 为什么"容器里是 root"比"宿主上是 root"风险低？低在哪一层？如果挂载了 `docker.sock` 或用了 `--privileged`，这个结论还成立吗？ |
| 自检 | 能说出 ≥3 个"写 Dockerfile 的安全习惯" |
