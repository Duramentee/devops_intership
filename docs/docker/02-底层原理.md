# Docker 底层原理 · 隔离 / 限制 / 分层

> 一句话总纲：**容器 = 一组 namespace（隔离"看得见什么"）+ cgroup（限制"能用多少"）+ 一个 rootfs（文件系统视图）的普通进程。**
> 与虚拟机最大的区别：**和宿主机共用同一个内核**。

---

## 一、namespace：隔离"视图"

| namespace | 隔离什么 | 造成的现象 |
|---|---|---|
| `pid` | 进程号 | 容器里 PID 1 的进程，在宿主上是另一个 PID（`docker exec` vs `ps -ef` 对比过） |
| `net` | 网卡、IP、端口、路由表 | 容器有独立 IP；`-p` 是宿主上的端口转发 |
| `mnt` | 挂载点 | 容器看到的是自己的 rootfs，不是宿主 `/` |
| `uts` | 主机名/域名 | 容器可以有自己的 hostname |
| `ipc` | 信号量、共享内存 | 跨容器共享内存需 `--ipc` |
| `user` | 用户/UID 映射 | 容器 root 可映射成宿主普通用户（`--userns-remap`） |

📖 namespace 与 cgroup 的机制说明：1.2 节（`k8s-in-action.txt` 行 2029-2326，PAGE 45-54；模块 `01-容器与K8s入门.md` §2）。

**三个推论（Day 1 已验）**
1. 容器里的进程在宿主 `ps` 里**看得见** —— 因为它就是宿主上的普通进程。
2. "启动快"不是玄学 —— 没有操作系统要引导，只是起了个进程。
3. 容器里 PID 1 死掉 = 容器退出 —— 容器生命周期**绑在 1 号进程**上。

## 二、cgroup：限制"资源"

| 控制器 | 限制 |
|---|---|
| `cpu` | CPU 配额/权重（`--cpus`、`--cpu-shares`） |
| `memory` | 内存上限，超了 → **OOMKill**（`-m 256m`） |
| `blkio` | 磁盘 IO 带宽 |
| `pids` | 进程数上限（防 fork 炸弹） |

⚠️ 被 OOMKill 时容器退出码是 **137**，`docker inspect` 里 `State.OOMKilled=true`（见 `05-排障索引.md`）。
✍️ cgroup v1（多层级）与 v2（统一层级）行为不同，`docker info` 可看当前版本。K8s 侧的 `resources.limits` 就是翻译成 cgroup 参数。

## 三、镜像分层与写时复制（今天的主线）

### 结构

```
        ┌────────────────────┐  ← 可写层（容器层，容器删了就没了）
        │  container layer   │
        ├────────────────────┤
        │  layer N (只读)     │  ← Dockerfile 的第 N 条指令
        ├────────────────────┤
        │      ...           │
        ├────────────────────┤
        │  layer 1 (只读)     │  ← Dockerfile 的第 1 条指令
        ├────────────────────┤
        │  base image layers │  ← FROM 的基础镜像
        └────────────────────┘
```

📖 **原话**："构建镜像时，Dockerfile 中每一条单独的指令都会创建一个新层。"（2.1.4 节，行 3104-3114）
📖 镜像分层 + 顶层可写层 + 写入时复制：模块 `01-容器与K8s入门.md` §3（书 p.53）。

### 写时复制（Copy-on-Write）

| 动作 | 发生什么 |
|---|---|
| 容器**读**一个只读层里的文件 | 直接读，不复制 |
| 容器**改/删**它 | 从下层**复制到可写层（copy-up）**再改；下层原文件不动 |
| 容器删掉该文件 | 可写层加一条"白障（whiteout）"记录，下层仍在 |

**两个必背后果**
1. 多个容器共享同一只读层 → 省磁盘、启动快。
2. 数据写在可写层里 → **`docker rm` 就没了**；要持久化必须用 **volume / bind mount**（Day 4）。

## 四、构建缓存规则（Day 2 实验的机制）

| 问题 | 答案 |
|---|---|
| 缓存以什么为单位？ | **层**。每条指令一层，逐层比对 |
| 什么时候失效？ | 该指令的输入变了（如 `COPY` 的文件内容变了、`RUN` 的命令字符串变了） |
| 失效范围？ | **从失效那一层开始，之后的层全部重建**（后面不再复用旧缓存） |
| 为什么顺序重要？ | 把"常变的"放后面，能让前面"不变的层"一直命中 |

⚠️ `RUN go mod download` 会不会重跑，取决于**它前面 `COPY` 进去的 `go.mod` 有没有变**：
- `COPY . .` 在前 → 改一行 `main.go` 也重装依赖；
- 只先 `COPY go.mod go.sum` 再 `RUN go mod download`，最后 `COPY . .` → 改代码不影响依赖层。
（这正是你自己要得出的结论 —— 见 Day 2 每日一题）

## 五、容器进程 vs 宿主进程（对照表）

| 视角 | 命令 | 看到什么 |
|---|---|---|
| 宿主 | `ps -ef \| grep webapp` | 容器的服务进程，PID 是宿主编号 |
| 容器内 | `docker exec <c> ps aux` | 同一个进程，PID 从 1 开始编号 |
| 宿主 | `docker ps` | 只有容器视角（PID 1 是谁、启动命令） |

## 六、capability：容器里的 root 为什么不是宿主 root（Day 6 实测）

> 一句话：**容器的权限 = uid（只是个数字）+ 一叠"能力位"。真正决定"能干什么"的是位图，不是 uid。**

### 6.1 三道闸门（全都是在内核里"做减法"）

| 闸门 | 削弱什么 | 造成的现象 |
|---|---|---|
| namespace | **视野**：看不见宿主的进程 / 文件树 / 网络栈 | 想动宿主资源时，**路径上根本没这个对象** |
| **capability** | **能力**：把 root 的全能拆成 ~40 个位，只留一部分 | `mount`、加载内核模块、ptrace 宿主 → `Operation not permitted` |
| seccomp / AppArmor | **系统调用**：默认 profile 过滤一批 syscall | 某些 syscall 直接返回错误 |

⚠️ **推论（关键）**：三道闸门都在内核里，一旦有路径绕过（错配 `--privileged`、挂 `docker.sock`、内核漏洞），进程**本来就是 uid=0 + 带能力位** → **立刻等价于宿主 root**。
→ 所以规范做法是**根本不用 root 跑**：非 root 就算逃逸，最好也只是个普通用户。

### 6.2 `/proc/<pid>/status` 里的 5 个 Cap 字段

| 字段 | 含义 |
|---|---|
| `CapBnd` | **天花板**：本进程一生能拿到的能力上限。`exec` 一个 setuid-root 程序也只能涨到 Bnd 以内 |
| `CapPrm` | 当前**可用**的能力 |
| `CapEff` | 当前**生效**的（平时 = `CapPrm`） |
| `CapInh` / `CapAmb` | 跨 `execve` 传递用（inheritable / ambient），容器里默认全 0 |

### 6.3 位图怎么读（本机实测）

`docker run --rm alpine:3.22 grep ^Cap /proc/self/status` 默认输出：

```
CapPrm: 00000000a80425fb
CapEff: 00000000a80425fb
CapBnd: 00000000a80425fb
```

按**字节**拆 `0xa80425fb`，每一位 = 一个能力（cap 编号 = 位号）：

| 字节 | 二进制 | 置 1 的位 → 能力名 |
|---|---|---|
| `0xfb` | `1111 1011` | 0 `CHOWN` · 1 `DAC_OVERRIDE` · 3 `FOWNER` · 4 `FSETID` · 5 `KILL` · 6 `SETGID` · 7 `SETUID`（缺位 2 `DAC_READ_SEARCH`） |
| `0x25` | `0010 0101` | 8 `SETPCAP` · **10 `NET_BIND_SERVICE`** · **13 `NET_RAW`** |
| `0x04` | `0000 0100` | 18 `SYS_CHROOT` |
| `0xa8` | `1010 1000` | 27 `MKNOD` · 29 `AUDIT_WRITE` · 31 `SETFCAP` |

**数出来正好 14 个** = Docker 默认清单（与文档一致，可互相验证）。下面这几位**默认是 0**，也是逃逸最常被利用的：

| 位 | 能力 | 意味着什么 |
|---|---|---|
| 12 | `NET_ADMIN` | 改路由 / iptables / 网络设备 |
| 16 | `SYS_MODULE` | 加载内核模块 |
| 19 | `SYS_PTRACE` | ptrace 别人的进程 |
| 21 | `SYS_ADMIN` | 挂载/卸载文件系统等一大堆特权 |

`--cap-drop=ALL` 之后 **Eff / Prm / Bnd 全变 `0000000000000000`** → 连"镜像里藏 setuid root 二进制再提权"也堵死。

### 6.4 逃逸 / 破防的典型路径

| 场景 | 为什么等于宿主 root（多数不是漏洞，是"合法"配置） |
|---|---|
| `-v /var/run/docker.sock:/var/run/docker.sock` | 通过这个 socket 可以命令宿主 dockerd 起一个 `--privileged` 容器并挂载宿主 `/` |
| `--privileged` | 关掉能力减法 + 给几乎所有能力 + 放行设备 |
| `--pid=host` + `CAP_SYS_PTRACE` | 能 ptrace / 杀宿主进程 |
| `-v /:/host` | 直接读写宿主文件树（改 `/etc/cron.d` = root 持久化） |
| 内核漏洞（DirtyCow 等） | 唯一**需要真漏洞**的路径 |

→ 命令怎么查、怎么配：`03-命令词典.md` §七（选项大表）+ §十（三段式与易错点）

### 6.5 案例：容器里不是 root 也能 `ping` —— ICMP 的两条路（本机 A/B/C 实测）

现象：`--cap-drop=ALL`（连 `NET_RAW` 都被砍了）之后 `ping 8.8.8.8` **依然成功**，与"raw socket 需要 CAP_NET_RAW"矛盾。

| 组 | 命令改动 | 实测结果 |
|---|---|---|
| A | 只读 `net.ipv4.ping_group_range` | `0\t2147483647` ← **Docker 默认注入**（内核默认是 `1 0` = 空区间） |
| B | A 基础上把区间掏空 `--sysctl net.ipv4.ping_group_range='1 0'`（仍无 `NET_RAW`） | ❌ `ping: permission denied (are you root?)`，退出码 1 |
| C | B 基础上 `--cap-add=NET_RAW` | ✅ 回包正常，退出码 0 |

| 路 | 系统调用 | 内核检查什么 | 开关 |
|---|---|---|---|
| raw | `socket(AF_INET, SOCK_RAW, IPPROTO_ICMP)` | `ns_capable(net->user_ns, CAP_NET_RAW)` | `--cap-add=NET_RAW` |
| datagram | `socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)` | 进程 gid 是否落在 `net.ipv4.ping_group_range` 区间内 | `--sysctl net.ipv4.ping_group_range=...` |

**排除法证明**：原始那次 `--cap-drop=ALL` 成功时，raw 路**不可能**（`CAP_NET_RAW`=0）→ 它走的**一定是 datagram 路**；B 把两条路都关了 → `EPERM`；C 只打开 raw → 又通。两条路**各自独立**、各有开关。

⚠️ **结论**：**"Docker 的默认值" ≠ "最小权限"**。`--cap-drop=ALL` 只砍能力位，**Docker 主动放宽的 sysctl 口子还在**；要真收紧得连它一起关。
⚠️ 报错文案会骗人：`ping: permission denied (are you root?)` 是 busybox 写的，它真正缺的是**能力位/区间**，不是 root 身份。

### 6.6 第二个案例：绑低端口的权限到底由什么决定（本机 K/F/E/G 矩阵实测）

**先量底料**：`net.ipv4.ip_unprivileged_port_start` 内核默认 `1024`，**Docker 默认给它 `0`**。

**内核对 bind 的实际判定式**（两个条件**同时**成立才拒）：

```
拒绝 ⟺ (端口 < net.ipv4.ip_unprivileged_port_start) 且 (进程 CapEff 里没有 CAP_NET_BIND_SERVICE)
```

**实测矩阵（阈值 = 1024）**

| 组 | uid | `CapEff` 里的 `NET_BIND_SERVICE` | 绑 80 结果 | 结论 |
|---|---|---|---|---|
| F2 | **0** | ✗（`--cap-drop=ALL`） | ❌ `nc: bind: Permission denied` | uid=0 也照样被拒 → **"是 root 就能绑低端口"被证伪** |
| K4 | **0** | ✓（drop ALL + add） | ✅ 绑上（退出码 143 = 被 `timeout` 杀掉） | 同一个 uid，**唯一位图不同 → 结果相反** |
| E2 | 10001 | 名义上有（默认清单含它） | ❌ 被拒 | 见下：**非 root 时 P/E 被清空** |
| G2 | 10001 | ✓（drop ALL + add） | ❌ 被拒 | 同上 |
| 阈值 = 0 时（D/E/F/G、K5） | 任意 | 任意 | ✅ **全都能绑** | 判定式第一个条件永不成立 → 能力位不参与判定 |

**非 root 为什么拿不到位（`/proc/self/status` 决定性测量）**

| 组 | 身份 | `CapPrm` / `CapEff` | `CapBnd` |
|---|---|---|---|
| K1 | root + 默认 | `a80425fb` | `a80425fb` |
| K2 | **非 root + 默认** | **`0000000000000000`** | `a80425fb` |
| K3 | **非 root + drop ALL + add `NET_BIND_SERVICE`** | **`0000000000000000`** | **`0x400`**（= 位 10 = `NET_BIND_SERVICE`） |

→ **结论**：**非 root 时 `CapPrm`/`CapEff` 被内核清空**（`setuid` 到非 0 uid 时发生），`--cap-add` **只写进 `CapBnd`（天花板），进不了 P/E**。
→ 这就是 §6.2 「Bnd = 一生能拿到什么，Eff = 现在能不能用」的现场兑现：K3 的 Bnd 有那个位、Eff 是 0 → **一点用都没有**。
→ 要让非 root 真正拿到能力，只能靠 **file capabilities**（`setcap`）或 **ambient caps**，容器层的 `--cap-add` 做不到。

**实践结论（记这两条就够）**

| 场景 | 正确做法 |
|---|---|
| 服务要跑成非 root | **绑高位端口（> 1024，如 8080）**，不要绑 80 |
| 对外必须暴露 80/443 | **宿主侧映射**：`-p 80:8080`（宿主 dockerd 以 root 绑 80，容器内仍是高位端口 + 非 root） |

⚠️ **实验设计教训（本机真实踩过）**：不把 sysctl 调回 `1024` 就去测 `NET_BIND_SERVICE`，四组（root/非root × 有/无能力）会**全部成功**，唯一区别只剩 `timeout` 的退出码 143 —— **变量没控住，结论就是假的**。正确做法：`docker run --sysctl net.ipv4.ip_unprivileged_port_start=1024 ...`，**并在每组前后都 `cat` 一次底料**。

✍️ **推断（未验证，勿当结论）**：K2 的 `CapBnd` 保留了默认 14 个位 → 镜像内若存在 **setuid-root** 的二进制，非 root 进程执行它可能把 Bnd 里的位"激活"回 P/E。这也是为何加固时要：镜像里清 setuid（`find / -perm -4000`）+ 运行时 `--security-opt no-new-privileges`。

✍️ **排障提示**：`nc` 这类工具在"绑定成功、在监听"时会输出 `punt!`（本机实测：**只在成功路径出现**，被拒时输出的是 `Permission denied`）。**判定一律用退出码，不看文案**。

### 6.7 Docker 主动放宽的默认值（实测汇总）⚠️ 默认值 ≠ 最小权限

| 参数 | 内核默认 | **Docker 默认** | 影响 |
|---|---|---|---|
| `net.ipv4.ping_group_range` | `1 0`（空区间） | `0 2147483647` | 任何 gid 都能建 ICMP datagram socket → 不用 root、不用 `NET_RAW` 也能 `ping` |
| `net.ipv4.ip_unprivileged_port_start` | `1024` | `0` | 任何 uid 都能绑低端口 → 不需要 `NET_BIND_SERVICE` |

→ **推论**：`--cap-drop=ALL` 只砍能力位；**Docker 自己放宽的那些口子还在**。想真收紧，得额外显式 `--sysctl` 覆盖。

## 七、常见误区

| 误区 | 事实 |
|---|---|
| "容器是轻量虚拟机" | 共用宿主内核，没有 guest 内核、没有硬件虚拟化 |
| "容器里 root = 宿主 root" | 差一个 namespace + capability，但**逃逸后≈宿主 root**（见 §六） |
| "镜像里删了文件镜像就变小" | 下层文件还在，只是加了白障；要变小得靠**多阶段构建**（Day 3） |
| "`docker restart` 会保住数据" | 数据在可写层，容器不删就还在；**删容器就没了** |
