# Docker 底层原理 · 隔离 / 限制 / 分层

> 一句话总纲：**容器 = 一组 namespace（隔离"看得见什么"）+ cgroup（限制"能用多少"）+ 一个 rootfs（文件系统视图）的普通进程。**
> 与虚拟机最大的区别：**和宿主机共用同一个内核**。

---

## 一、namespace：隔离"视图"

| namespace | 隔离什么 | 造成的现象 |
|---|---|---|
| `pid` | 进程号 | 容器里 PID 1 的进程，在宿主上是另一个 PID（`docker exec` vs `ps -ef` 对比过） |
| `net` | 网卡、IP、端口、路由表 | 容器有独立 IP；`-p` 是宿主上的端口转发 |
| `mnt` | 挂载点 | 容器看到的是自己的 rootfs，不是宿主 `/` |
| `uts` | 主机名/域名 | 容器可以有自己的 hostname |
| `ipc` | 信号量、共享内存 | 跨容器共享内存需 `--ipc` |
| `user` | 用户/UID 映射 | 容器 root 可映射成宿主普通用户（`--userns-remap`） |

📖 namespace 与 cgroup 的机制说明：1.2 节（`k8s-in-action.txt` 行 2029-2326，PAGE 45-54；模块 `01-容器与K8s入门.md` §2）。

**三个推论（Day 1 已验）**
1. 容器里的进程在宿主 `ps` 里**看得见** —— 因为它就是宿主上的普通进程。
2. "启动快"不是玄学 —— 没有操作系统要引导，只是起了个进程。
3. 容器里 PID 1 死掉 = 容器退出 —— 容器生命周期**绑在 1 号进程**上。

## 二、cgroup：限制"资源"

| 控制器 | 限制 |
|---|---|
| `cpu` | CPU 配额/权重（`--cpus`、`--cpu-shares`） |
| `memory` | 内存上限，超了 → **OOMKill**（`-m 256m`） |
| `blkio` | 磁盘 IO 带宽 |
| `pids` | 进程数上限（防 fork 炸弹） |

⚠️ 被 OOMKill 时容器退出码是 **137**，`docker inspect` 里 `State.OOMKilled=true`（见 `05-排障索引.md`）。
✍️ cgroup v1（多层级）与 v2（统一层级）行为不同，`docker info` 可看当前版本。K8s 侧的 `resources.limits` 就是翻译成 cgroup 参数。

## 三、镜像分层与写时复制（今天的主线）

### 结构

```
        ┌────────────────────┐  ← 可写层（容器层，容器删了就没了）
        │  container layer   │
        ├────────────────────┤
        │  layer N (只读)     │  ← Dockerfile 的第 N 条指令
        ├────────────────────┤
        │      ...           │
        ├────────────────────┤
        │  layer 1 (只读)     │  ← Dockerfile 的第 1 条指令
        ├────────────────────┤
        │  base image layers │  ← FROM 的基础镜像
        └────────────────────┘
```

📖 **原话**："构建镜像时，Dockerfile 中每一条单独的指令都会创建一个新层。"（2.1.4 节，行 3104-3114）
📖 镜像分层 + 顶层可写层 + 写入时复制：模块 `01-容器与K8s入门.md` §3（书 p.53）。

### 写时复制（Copy-on-Write）

| 动作 | 发生什么 |
|---|---|
| 容器**读**一个只读层里的文件 | 直接读，不复制 |
| 容器**改/删**它 | 从下层**复制到可写层（copy-up）**再改；下层原文件不动 |
| 容器删掉该文件 | 可写层加一条"白障（whiteout）"记录，下层仍在 |

**两个必背后果**
1. 多个容器共享同一只读层 → 省磁盘、启动快。
2. 数据写在可写层里 → **`docker rm` 就没了**；要持久化必须用 **volume / bind mount**（Day 4）。

## 四、构建缓存规则（Day 2 实验的机制）

| 问题 | 答案 |
|---|---|
| 缓存以什么为单位？ | **层**。每条指令一层，逐层比对 |
| 什么时候失效？ | 该指令的输入变了（如 `COPY` 的文件内容变了、`RUN` 的命令字符串变了） |
| 失效范围？ | **从失效那一层开始，之后的层全部重建**（后面不再复用旧缓存） |
| 为什么顺序重要？ | 把"常变的"放后面，能让前面"不变的层"一直命中 |

⚠️ `RUN go mod download` 会不会重跑，取决于**它前面 `COPY` 进去的 `go.mod` 有没有变**：
- `COPY . .` 在前 → 改一行 `main.go` 也重装依赖；
- 只先 `COPY go.mod go.sum` 再 `RUN go mod download`，最后 `COPY . .` → 改代码不影响依赖层。
（这正是你自己要得出的结论 —— 见 Day 2 每日一题）

## 五、容器进程 vs 宿主进程（对照表）

| 视角 | 命令 | 看到什么 |
|---|---|---|
| 宿主 | `ps -ef \| grep webapp` | 容器的服务进程，PID 是宿主编号 |
| 容器内 | `docker exec <c> ps aux` | 同一个进程，PID 从 1 开始编号 |
| 宿主 | `docker ps` | 只有容器视角（PID 1 是谁、启动命令） |

## 六、常见误区

| 误区 | 事实 |
|---|---|
| "容器是轻量虚拟机" | 共用宿主内核，没有 guest 内核、没有硬件虚拟化 |
| "容器里 root = 宿主 root" | 差一个 namespace + capability，但**逃逸后≈宿主 root**（Day 6） |
| "镜像里删了文件镜像就变小" | 下层文件还在，只是加了白障；要变小得靠**多阶段构建**（Day 3） |
| "`docker restart` 会保住数据" | 数据在可写层，容器不删就还在；**删容器就没了** |
