# Docker 排障索引（现象 → 机制 → 命令）

> 用法：**先查现象，不要先查命令。** 面试和真实故障都是按现象提问的。
> 与 `docs/linux/Linux-故障索引.md` 配对使用：容器问题常常也是 Linux 问题（fd、inode、磁盘、端口）。
> 🧭 查具体知识点：`docs/00-知识点索引.md` §1-G（排障）· §3（按现象）

## 一、五步定位法（无条件按顺序走）

| 步 | 问什么 | 命令 |
|---|---|---|
| 1 | **容器还在吗** | `docker ps -a`（看 STATUS 列，退出码就在里面） |
| 2 | **它是怎么退的** | `docker inspect 名 --format '{{.State.ExitCode}} oom={{.State.OOMKilled}} {{.State.StartedAt}} → {{.State.FinishedAt}} {{.State.Error}}'`（`State.Error` 是 `Created` 容器**唯一**的线索） |
| 3 | **日志最后说了什么** | `docker logs --tail 100 名` |
| 4 | **环境对不对** | ⚠️ 容器**在跑**：`docker exec -it 名 sh`；**已退出**：`docker run --rm -it --entrypoint sh 镜像:tag` 或 `docker cp 名:/路径 /tmp/` |
| 5 | **资源够不够** | 容器**在跑**：`docker stats --no-stream`；看历史**限制值**：`docker inspect -f '{{.HostConfig.Memory}}' 名`；磁盘 `docker system df` |

⚠️ 顺序有意义：**先看"在不在"，再看"为什么退"**。反过来会浪费时间 —— 容器都不在，`exec`/`stats` 必然失败（见 §二「按退出码排障」末尾的对照表）。

## 二、退出码速查

> **先分类**：`125/126/127` = **容器里的命令压根没跑起来** → 查**镜像 / Dockerfile**；其余 = **进程活过** → 查**应用 / 资源 / 信号**。顺序别反 —— 容器都不在，`exec` / `stats` 必然失败。

| 码 | 信号 | 谁的问题 · 常见原因 | 第一步命令 |
|---|---|---|---|
| `0` | — | **容器设计**：CMD 是"跑完就退"的脚本、应用默认后台化 → 主进程退出 | `docker inspect -f '{{.Config.Cmd}} {{.Config.Entrypoint}}' 名`，再 `--entrypoint sh` 手动跑一遍 |
| `1` | — | **应用自己** `exit(1)`：配置错、依赖缺、端口被占、连不上 DB | `docker logs --tail 200 名`，再 `--entrypoint sh` 进去逐条复跑 |
| `2` | — | 应用/脚本参数错（usage）；⚠️ 也可能是 **Go 做 PID 1 时的信号回退码**（见下） | `docker logs 名` |
| `125` | — | **docker CLI/daemon**：参数非法（报错打在**终端**，不在容器里） | 看 `docker run` 的原始报错 |
| `126` | — | 命令**存在但不可执行**：缺 `+x`、架构不匹配、在 `noexec` 挂载（如 `--tmpfs`）里 | `docker run --rm --entrypoint sh 镜像 -c 'ls -l /app'` |
| `127` | — | 找不到命令：CMD/ENTRYPOINT 指向**不存在**的文件、命令名拼错、`PATH` 找不到 | `inspect -f '{{.Config.Cmd}}'` → `docker history 镜像` 看 COPY 那层 |
| `137` | `128+9` | 被 **SIGKILL**：⚠️ **不是 OOM 专属码** —— OOM、`docker kill`/`rm -f`、stop 超时升级、宿主 OOM 都给 137 | `inspect -f '{{.State.OOMKilled}} {{.State.StartedAt}} → {{.State.FinishedAt}}'` → `docker events --since <Start> --until <Finish>` |
| `139` | `128+11` | 段错误：二进制/依赖不匹配（musl vs glibc、CGO 没静态化）、多阶段 COPY 错产物 | 前台跑看崩溃输出；`file` / `ldd` |
| `143` | `128+15` | 收到 **SIGTERM**：`docker stop`/`restart`、daemon 重启、K8s 删 Pod —— 属**正常流程**，不是故障 | 先问"**是不是我自己 stop 的**"：`docker events --since <Finish-1m>` |
| `255` | — | 应用/脚本显式 `exit -1` | `docker logs 名` → 手动复跑 |

⚠️ `137` 与 `143` 的区别是"优雅关闭"的核心：**143 是"请你退"，进程有机会善后；137 是"直接打死"，没有机会。**

#### ⚠️ 容器已退出时，哪些命令**不能**用

| 命令 | 对已退出容器 | 替代 |
|---|---|---|
| `docker exec` | ❌ `Error response from daemon: Container ... is not running` | `docker run --rm -it --entrypoint sh 镜像:tag`；`docker cp 名:/路径 /tmp/`；`docker commit 名 调试:快照` |
| `docker stats` | ❌ 只统计**运行中**的 cgroup | 看限制值 `docker inspect -f '{{.HostConfig.Memory}}' 名`；要看实时占用得**趁容器在跑时**另开终端 |
| `docker top` | ❌ 同上 | `docker inspect -f '{{.State.Pid}}' 名`（已退出时为 `0`） |
| `docker logs` | ✅ 仍可用 | 日志存在容器的 json-log 里 |
| `docker inspect` | ✅ 最可靠的现场 | — |
| `docker diff` | ✅（只要容器没删） | 看可写层改了什么 |
| `docker cp` | ✅（只要容器没删） | 捞文件出来 |

#### ⚠️ 三条会颠覆直觉的实测结论

#### ① `docker stop` 的结局由「PID 1 是谁 + 装没装 handler」决定 —— `143` 反而是最少见的那个

同一份 Go 程序，6 组实验（A–F）得到 **4 种不同退出码**：PID 1 不装 handler → `2`；装了 `Notify` 并善后 → `0`；只 `Ignore` → `137`（等超时被 SIGKILL）；**Go 作为子进程**（非 PID 1）→ `143`。容器自身做 PID 1 且不处理信号时（`sh -c 'sleep 600'`、直接 `sleep 600`）同样是 `137` + 等满 `-t 3`。
原始实验数据与复跑脚本：`code/week1/day5/logs/`、`run.sh` / `run2.sh`。

**机制链（一句话）**：内核对 **PID 1** 有 init 保护 —— **默认处置为"终止"的信号会被忽略**（SIGKILL/SIGSTOP 除外），除非进程自己装了 handler ⇒ 不装 handler 的 PID 1 只能等超时被 SIGKILL（→137）；而 **Go runtime 给所有信号都装了内部 handler**，没注册 `Notify` 时走 `dieFromSignal()`：置回 `SIG_DFL` → `raise(SIGTERM)` → 若信号没杀死进程就**回退 `exit(2)`**（所以 A 组是 `2`，非 PID 1 的 F 组才是 `143`）。

**三条推论**

| # | 结论 |
|---|---|
| 1 | `0` / `2` / `137` / `143` **都是 `docker stop` 可能的结局** —— 不看「PID 1 是谁 + 装没装 handler」就无法预判，也**不能用退出码反推"是不是故障"** |
| 2 | ⚠️ **"优雅关闭成功"的标志是 `ExitCode 0` + 日志里有善后输出**（实验 B）；`Exited (143)` 只说明"被 SIGTERM 杀死"，**善后可能压根没发生** |
| 3 | 想让服务**收到**信号：① `CMD`/`ENTRYPOINT` 用 **exec 形式**（应用自己当 PID 1）② 代码里显式装 handler ③（可选）加 `--init`（tini） |

#### ② `127` 有两种形态：一种有 `Exited`，一种**根本没有 `Exited`**

| CMD 形式 | Docker 实际执行 | `ps -a` 显示 | ExitCode | `docker logs` | 线索在哪 |
|---|---|---|---|---|---|
| `CMD ["/app/not-exist"]` | runc 直接 `exec` | **`Created`** | `127` | **空** | `State.Error`（runc 原文报错） |
| `CMD /app/not-exist` | `/bin/sh -c "/app/not-exist"` | `Exited (127)` | `127` | `/bin/sh: ... not found` | `docker logs` |

- `Created` 容器特征：`StartedAt`/`FinishedAt` = **`0001-01-01T00:00:00Z`**（Go 零值）、`Pid=0`、`docker start` 重试仍失败（CLI 退出码 `1`）
- 旁证：`docker build` 对 shell 形式 CMD 会**警告** —— `JSONArgsRecommended: JSON arguments recommended for CMD to prevent unintended behavior related to OS signals`

#### ③ 三个"工具会骗你"的点

| 坑 | 实测现象 | 正确做法 |
|---|---|---|
| 以为 `-m 32m` 是硬限制 | 吃到 **56 MiB** 才 OOM | `MemorySwap` **默认 = 2 × Memory**；要硬限制：`--memory-swap` 设成与 `-m` **相同** |
| `docker events --until <FinishedAt>` | `oom` / `die` 事件**完全看不到**（事件时间戳晚于 `FinishedAt`） | `--until` 用**"现在"或更晚**；`die` 事件自带 `exitCode` + `execDuration` |
| `docker stats` 查已退出容器 | 返回 **`0B / 0B`、`PIDS=0`，而且不报错**（假数据，看着像容器闲着） | 先 `docker inspect -f '{{.State.Status}}' 名` 确认在跑 |

### curl 退出码（客户端侧的另一套编码）

> ⚠️ 别混：`Exited (137)` 是**容器进程**的退出码（由 docker 记录）；`curl: (56)` 是 **curl 自己**的退出码（客户端没连上 / 没收到数据）。
> 价值：curl 的码告诉你**失败发生在哪一段**，是网络排障的第一把尺子（配合 §三「报错前缀」使用）。

| 码 | 文案（典型） | 失败在哪一段 | 先查什么 |
|---|---|---|---|
| **7** | `Failed to connect ... Connection refused` | **SYN 阶段**被 RST → 目标侧**没人 listen** | `-p` 写了吗（`docker port 名`）；`ss -ltnp \| grep <宿主端口>` |
| **56** | `Recv failure: Connection reset by peer` | TCP 连接**已被接受**后被 RST / 关闭 → 包**到了目标**，但**那个端口没人 listen** | 应用真正 listen 的端口：`docker exec 名 netstat -tlnp` |
| **28** | `Connection timed out` | 包被**静默丢弃**（DROP，不是 REJECT） | 防火墙 / 安全组 / 路由 —— **别往应用上找** |
| **52** | `Empty reply from server` | 连上了、服务接受了连接，但**没返回任何数据**就关了 | `docker logs 名`（应用崩了 / 协议不对） |
| **6** | `Could not resolve host` | DNS 解析失败 | 容器内 `/etc/resolv.conf`；是否在自定义网络里 |

**口诀**：7 = 找不到门；56 = 门开了但屋里没人；28 = 敲门没人应也没人拒；52 = 有人应了但一句话不说。

**为什么「`-p 8082:8081` 但应用听 8080」报 56 而不是 7**：localhost 访问发布端口时走 **docker-proxy** —— 它先在宿主**接受**你的连接（握手成功），再往里连、失败则关掉 → 客户端看到 `ECONNRESET`（56），而不是 `ECONNREFUSED`（7）。
用 `curl -v` 看卡在 `Trying <ip>...` 还是 `Connected to ...` 之后，一眼分辨 7 / 56。

## 三、现象索引表（主表）

| 现象 | 先想哪个机制 | 第一条命令 |
|---|---|---|
| 容器起来就退出 | 主进程结束 = 容器结束；CMD 指向错 | `docker logs 名`、`docker inspect 名`（ExitCode） |
| `Exited (0)` | 主进程"跑完了"，容器不是常驻的 | `docker inspect -f '{{.Config.Cmd}}' 名`；把它**前台化** |
| `Exited (1)` / `(2)` | 应用自己 `exit(n)` | `docker logs --tail 200 名`；进容器手动复跑 |
| `Exited (125)` | `docker run` 参数非法（报错在终端，不在容器里） | 复制终端原始报错 |
| `Exited (126)` | 命令**存在但不可执行** | `docker run --rm --entrypoint sh 镜像 -c 'ls -l /app'`；查 `noexec` |
| `Exited (127)` | CMD/ENTRYPOINT 指向的文件不存在 | `docker history` 看构建指令；已退出容器只能 `--entrypoint sh` 重新起 |
| `Exited (137)` | 被 SIGKILL：**OOM / 人杀的 / stop 超时** | `docker inspect 名 \| grep -i oomkilled` ①再看 `docker events` |
| `Exited (139)` | 段错误（二进制/依赖不匹配） | `docker run --rm -it 镜像` 前台观察；`file` / `ldd` |
| `Exited (143)` | 收到 SIGTERM（正常停止流程） | 对比是不是自己 `docker stop` 的；看应用有没有优雅退出日志 |
| `Exited (255)` | 应用/脚本显式 `exit -1` | `docker logs 名` |
| 状态是 **`Created`**（没有 `Exited`） | runc 在 **create 阶段**就失败：CMD 指向不存在的文件、权限、rootfs 问题 | `docker inspect -f '{{.State.Error}}' 名` |
| `Up (unhealthy)` | **不是退出**，是 HEALTHCHECK 失败 | `docker inspect -f '{{json .State.Health}}' 名` |
| 容器名冲突 | 已存在同名容器 | `docker ps -a`、`docker rm -f 名` |
| 端口被占用 / 起不来 | 宿主端口已被别人监听 | `ss -tlnp \| grep 8080`、`docker port 名` |
| `curl localhost:8080` 不通 | `-p` 没写或写反 / 服务只监听 127.0.0.1 | `docker port 名`；容器内 `curl localhost:8080` 自测 |
| 容器内能访问、宿主不能 | 服务绑 `127.0.0.1` 而非 `0.0.0.0` | 改应用监听地址 |
| `docker exec` 报 `no such file` | 镜像里没有 sh（scratch/distroless） | 换 `--entrypoint /app/xxx` 或改用 `docker cp` + 日志 |
| 日志空空如也 | 日志写进文件而非 stdout | 让应用输出到 stdout，或 `docker exec` 进去 `cat` 日志文件 |
| 磁盘满 | 镜像层 + 可写层 + 卷 + 构建缓存 | `docker system df`、`docker system prune`（⚠️ 先看清再删） |
| 数据"重启就丢" | 写在可写层，容器重建即失 | 用 `-v 卷:/路径`；`docker inspect 名` 看 Mounts |
| `docker pull` 失败 | 网络/代理/认证/镜像不存在 | `docker pull nginx:1.27` 试基础镜像；检查 `~/.docker/config.json` |
| `docker build` 失败 | 上下文不对、COPY 找不到文件、网络 | 看输出**最后 3 行**；确认文件在上下文里 |
| 构建特别慢 | 上下文太大、缓存未命中 | `.dockerignore`；`docker build --progress=plain` 看细节 |
| 改了代码但镜像没变 | 复用了缓存 / 起的是旧容器 | build 时看 `CACHED`；⚠️ 记得 `docker rm` 旧容器再 `run` |
| 改了代码重装依赖 | `COPY . .` 在 `RUN 安装依赖` 之前 | 调整指令顺序（见 `04` 第四节） |
| 容器里 root、权限怪 | 镜像默认 root + capability | `USER`、`--cap-drop`、`--read-only`（Day 6） |
| 时区/编码不对 | 镜像里没有 tzdata / locale | `-e TZ=Asia/Shanghai`、基础镜像自带 |
| 想不起来 `-p` 语法 | 宿主:容器 | `-p 宿主端口:容器端口` |

### 报错前缀 = 谁在说话

> 读报错第一件事：**看前缀属于哪一层**。Docker 的错误是分层往上冒的，前缀直接告诉你去哪一层找。

| 前缀 / 形态 | 谁报的 | 意味着 |
|---|---|---|
| `OCI runtime exec failed:` | **runc**（容器运行时，dockerd 的下一层） | 进程**根本没起来**：找不到可执行文件、权限不足、rootfs 有问题 |
| `Error response from daemon:` | **dockerd** | daemon 层面的拒绝：容器在跑不许删、名字重复、参数非法 |
| `cat: can't open '...'` 之类 | 容器里的**应用 / shell** | 进程起来了，**业务层**出错（文件没了、参数不对） |
| `template parsing error:` | **docker CLI**（本地） | `-f` 的 Go 模板写错、或字段不存在（例：containerd 镜像存储下没有 `GraphDriver`） |
| `permission denied` / `no such file` | **内核 / 应用** | 权限、挂载、capability / seccomp 拦截 |

## 四、常用诊断命令组合

| 目的 | 命令 |
|---|---|
| 一眼看状态 | `docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'` |
| 一眼看退因 | `docker inspect 名 --format '{{.State.ExitCode}} oom={{.State.OOMKilled}} {{.State.Error}}'` |
| 看起止时间（活多久） | `docker inspect 名 --format '{{.State.StartedAt}} → {{.State.FinishedAt}}'` |
| **看"谁杀了它"**（退出码查不到的那一半） | `docker events --since <Start> --until <Finish>` |
| 只看 OOM 事件 | `docker events --filter event=oom --since 1h` |
| 只看某个容器的事件 | `docker events --filter container=名 --since 1h` |
| 看内存限制是多少 | `docker inspect 名 --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}'` |
| 看重启次数 | `docker inspect 名 --format '{{.RestartCount}}'` |
| 看健康检查结果 | `docker inspect 名 --format '{{json .State.Health}}'` |
| 看容器日志最后 50 行并跟随 | `docker logs --tail 50 -f 名` |
| 看容器内 PID 1 是什么 | `docker inspect 名 --format '{{.Config.Cmd}} {{.Config.Entrypoint}}'` |
| 忽略镜像入口直接进容器 | `docker run --rm -it --entrypoint sh 镜像:tag` |
| 看挂载 | `docker inspect 名 --format '{{json .Mounts}}'` |
| 看端口映射 | `docker port 名` |
| 看容器内进程（宿主视角） | `docker top 名` |
| 看谁占了宿主端口 | `ss -tlnp \| grep <端口>`（Linux 侧，见 `Linux-故障索引.md`） |
| 看磁盘明细 | `docker system df -v` |
| 容器改了啥 | `docker diff 名` |

## 五、极端情况

| 情况 | 处理 |
|---|---|
| 镜像没有 shell，进不去 | `docker cp` 拷文件进出；或用 `docker run --entrypoint` 指定其他入口；或本地起个同款镜像调试 |
| 容器卡在 D 状态（不可中断 IO） | 常见于挂载的 NFS/坏盘；`docker rm -f` 也可能失败，需查 `dmesg` |
| 想保留现场再删 | 先 `docker commit 名 调试:快照`（临时手段）或 `docker cp` 出日志 |
| `docker system prune -a` 删过头 | 镜像可重新拉取/构建；**卷删了 = 数据没了**，务必先 `docker volume ls` |
| 容器状态卡在 `Created` | 进程**从没跑起来**（runc create 阶段就失败）→ `docker logs` 是空的，只能看 `State.Error`；`docker start` 会再失败一次。要么改 Dockerfile 重建，要么 `docker rm` 掉 |
| `docker system prune` 到底会删什么 | **实测**：删**所有已停止的容器**（含 `Created`）+ 构建缓存；**有 tag 的镜像**和**全部卷**不受影响，运行中的容器安全 |
| 别顺手加 `-a` | `-a` 会删掉未使用的**有 tag 镜像**（`webapp:v1/v2/v3`、`kindest/node` 1.3GB+…）；先 `docker system df` + `docker ps -a --filter status=exited` 预检 |

## 六、待回填（学 K8s 时补）

| 现象 | 机制 |
|---|---|
| Pod `CrashLoopBackOff` | 退出码 + 重启策略 + 退避 |
| Pod `OOMKilled` | cgroup 内存 limit |
| Pod 一直 `Terminating` | 优雅终止期 + SIGTERM/SIGKILL（对应本文 137/143） |
| 镜像拉不下来（`ImagePullBackOff`） | 镜像名/私有仓库凭证/网络 |
