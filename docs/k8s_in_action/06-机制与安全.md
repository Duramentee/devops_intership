# 模块 06 · 集群内部机制与安全（第 11~13 章）

> 目标：能画出架构图、讲清"一个 Deployment 提交后发生了什么"，并会做基本的认证授权与网络隔离。

## 一、核心概念（整体观）

### 1. 控制平面四组件（p.483-533）

| 组件 | 职责 |
|---|---|
| etcd | 分布式一致 KV 存储，**唯一**持久化集群配置的地方 |
| API server | **唯一中枢**，所有组件都通过它通信；唯一直接读写 etcd 的组件 |
| 调度器 Scheduler | 给 Pod 选节点 |
| 控制器管理器 Controller Manager | 跑各种控制器（RS/Deployment/Node 等）|

工作节点：**Kubelet**（管理本节点容器、跑探针、上报状态）、**kube-proxy**（服务流量负载均衡）、容器运行时。

### 2. 三个关键机制

- **乐观并发控制**：每个对象带 `resourceVersion`，更新时版本不符就拒绝（p.487）。
- **API server 三阶段**：认证插件 → 授权插件 → 准入控制插件（可修改请求）→ 校验并持久化；读请求不做准入（p.491-493）。
- **控制器 = 调和循环**：监听 API 对象变更，把实际状态向 `spec` 期望状态收敛，把实际状态写进 `status`（p.498-499）。

### 3. 认证与 RBAC（p.535-576）

- 两类客户端：真实用户（外部系统管）、Pod 内应用（用 **ServiceAccount**）。
- SA 的 token 挂到 `/var/run/secrets/kubernetes.io/serviceaccount/token`，用户名格式 `system:serviceaccount:<ns>:<name>`。
- **RBAC 四资源**：
  - `Role`/`ClusterRole`：定义"能对哪些资源做什么动作"；
  - `RoleBinding`/`ClusterRoleBinding`：把角色绑到用户/组/SA。
  - Role/RoleBinding 命名空间级；ClusterRole/ClusterRoleBinding 集群级。
- 动词映射：get/list/watch→GET，create→POST，update→PUT，patch→PATCH，delete→DELETE。
- 默认 ClusterRole 分级：`view`（只读，不含 Secret）→ `edit` → `admin` → `cluster-admin`。
- **ClusterRole 双重用法**：绑 ClusterRoleBinding 跨全集群；绑 RoleBinding 只限该命名空间。但**集群级资源必须用 ClusterRoleBinding**。

### 4. 安全进阶（p.578-619）

- 宿主命名空间：`hostNetwork`、`hostPort`、`hostPID`、`hostIPC`。
- `securityContext`：`runAsUser`、`runAsNonRoot`、`privileged`、`capabilities add/drop`（去掉 `CAP_` 前缀）、`readOnlyRootFilesystem`、`fsGroup`。
- **PodSecurityPolicy(PSP)**：准入控制插件校验 pod 安全配置（⚠️ K8s 1.25 已移除，用 Pod Security Admission 替代）。
- **NetworkPolicy**：按标签选择器作用于 Pod，用 ingress/egress 规则限制流量；匹配来源三种：podSelector、namespaceSelector、CIDR。

## 二、关键细节

- **Deployment 事件链**（p.510-512）：kubectl POST → API server 存 etcd → Deployment 控制器建 RS → RS 控制器建 Pod → 调度器设 nodeName → Kubelet 拉镜像跑容器。
- 调度器两步：**过滤**（预测函数）→ **排序**（优先级函数）。
- kube-proxy 两种模式：userspace（真代理，轮询）、**iptables**（默认，仅内核改包目的地址，性能好但随机不均）。
- 高可用：etcd 用**奇数**实例（3/5/7，过半才能变更状态）；API server 无状态多实例；控制器/调度器用 `--leader-elect` 保证同时只有一个生效。
- 网络隔离先建 `default-deny` NetworkPolicy，再显式放行。

## 三、命令速查

| 场景 | 命令 / 字段 | 说明 |
|---|---|---|
| 控制面健康 | `kubectl get componentstatuses` | 各组件状态 |
| 监听变更 | `kubectl get pods --watch` | 实时通知 |
| 看 SA | `kubectl get sa` / `describe sa <n>` | |
| 建 SA | `kubectl create serviceaccount foo` | |
| Pod 指定 SA | `spec.serviceAccountName` | 创建后不可改 |
| 建 Role | `kubectl create role <n> --verb=get,list --resource=services -n foo` | |
| 建 RoleBinding | `kubectl create rolebinding <n> --role=<r> --serviceaccount=foo:default -n foo` | 绑用户 `--user`、组 `--group` |
| 限定实例 | 规则内 `resourceNames` | 特定资源实例 |
| 指定 API 组 | 规则内 `apiGroups` | |
| 建 ClusterRoleBinding | `kubectl create clusterrolebinding <n> --clusterrole=<r> --serviceaccount=foo:default` | 不带 `-n` |
| 宿主网络 | `spec.hostNetwork: true` | 用宿主接口 |
| 宿主端口 | `ports[].hostPort` | 绑宿主端口 |
| 指定用户 | `securityContext.runAsUser: 405` | |
| 禁 root | `runAsNonRoot: true` | |
| 特权 | `privileged: true` | 慎用 |
| 内核功能 | `capabilities.add: ["SYS_TIME"]` / `drop: ["CHOWN"]` | 无 CAP_ 前缀 |
| 只读根 FS | `readOnlyRootFilesystem: true` | |
| 建 NetworkPolicy | `kubectl create -f np.yaml` | 需 CNI 支持 |

## 四、易错点

1. 服务 IP 是虚拟的，ping 不通；iptables 模式数据包不进 kube-proxy 进程。
2. etcd 偶数实例反而更差（2 个比 1 个更容易整体不可用）。
3. RoleBinding 引用 ClusterRole **不能**授权集群级资源（PV 等），必须 ClusterRoleBinding。
4. 非资源 URL 的动词用小写 HTTP 动词 `get/post/put/patch`，不是 `create/update`。
5. `view` 角色故意不读 Secret（防止权限扩散）。
6. RBAC 启用后，默认 SA 几乎无权限。
7. hostPort 每节点只能调度一个副本（端口冲突）。
8. capabilities 写 `add/drop` 时去掉 `CAP_` 前缀。
9. PSP/NetworkPolicy 都只影响**新建** pod，不追溯已存在的。

## 五、动手实践

1. 画一遍架构图（控制平面 + 工作节点 + 组件间箭头），并口述 Deployment 事件链。
2. 建一个 SA，用 Role+RoleBinding 只授 `get,list services`，切换 `kubectl --as=system:serviceaccount:foo:default` 验证能 list service 但不能 list pods。
3. 建一个 ClusterRoleBinding 授权只读 PV，验证命名空间级 RoleBinding 做不到。
4. 建一个 `runAsNonRoot: true` 的 Pod，用一个默认以 root 运行的镜像，观察被拒绝。
5. 建 `default-deny` + 放行指定标签的 NetworkPolicy，验证隔离效果。
