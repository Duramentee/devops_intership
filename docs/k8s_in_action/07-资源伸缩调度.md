# 模块 07 · 资源、自动伸缩与调度（第 14~16 章）

> 目标：会配 requests/limits、看懂 QoS，会用 HPA 自动伸缩，会用污点/亲和性控制"Pod 放哪"。

## 一、核心概念（整体观）

### 1. requests 与 limits（p.621-643）

| 字段 | 含义 | 备注 |
|---|---|---|
| requests | 最小保证值 | **调度器只认这个** |
| limits | 最大硬限制 | 超限行为见下 |

- 按**容器**指定，Pod 资源量 = 各容器之和。
- **CPU 是可压缩资源**：超限被限流，不杀进程。
- **内存不可压缩**：超 limit 被 OOMKilled。
- **调度器只看 requests，不看实际使用量**（最反直觉的一点）。

### 2. QoS 等级（由配置推导，p.638-641）

| 等级 | 判定 |
|---|---|
| BestEffort | 所有容器都不设 requests 和 limits |
| Guaranteed | 每个容器每种资源 requests == limits |
| Burstable | 其余情况 |

**OOM 时杀谁**：先 BestEffort → 再 Burstable → 最后 Guaranteed；同级比 OOM 分数（实际用量/requests 比例高者先死）。

### 3. 限额两层（p.644-655）

- **LimitRange**：管单个 Pod/容器，设默认值和上下限（由 LimitRanger 准入插件强制）。
- **ResourceQuota**：管整个命名空间总量（CPU/内存/存储/对象个数）。

### 4. 自动伸缩（p.667-693）

| 类型 | 管什么 |
|---|---|
| HPA 横向 | 调整 Pod 副本数 |
| VPA 纵向 | 调整 Pod 的 requests/limits（本书时代未实现）|
| Cluster Autoscaler | 调整集群**节点**数 |

- **HPA 关键**：CPU 使用率 = 实际用量 ÷ **CPU requests**（所以必须设 requests）；HPA 只通过 Scale 子资源改 `replicas`。
- 伸缩有速率限制：副本>2 时单次最多翻倍；扩容距上次满 3 分钟，缩容 5 分钟——"该动不动"是正常的。

### 5. 高级调度（p.695-722）

| 机制 | 位置 | 作用 |
|---|---|---|
| 污点 taint | 节点上 | 拒绝 Pod 调度 |
| 容忍 toleration | Pod 上 | 容忍节点污点才能调度 |
| 节点亲和 nodeAffinity | Pod | 按节点标签"想去哪" |
| pod 亲和/反亲和 | Pod | 按**其他 Pod 的标签**协同/分散部署 |

- 污点三种效果：`NoSchedule`（硬阻）、`PreferNoSchedule`（软阻）、`NoExecute`（**还会驱逐**已运行的 Pod）。
- 亲和性用 `topologyKey` 控制"靠近程度"（同节点/机柜/可用区/地域）。

## 二、关键细节

- 容器内 `top` 显示的是**节点**的内存和全部核数，看不到自己的 limits → JVM 默认堆、按核数开线程的程序会踩坑（p.636）。
- 只设 limits 不设 requests 时，requests 默认 = limits → 直接变 Guaranteed。
- 建 ResourceQuota 时通常要配套建 LimitRange（否则新 Pod 没写 requests/limits 会被拒）。
- CPU 使用率可以**超过 100%**（分母是 requests，不是 limits）。
- HPA 目标指向 Deployment，别指底层 ReplicaSet（应用更新后预期副本数会丢）。
- 内存不适合做伸缩度量（扩容不会让原 Pod 少用内存，可能死循环）。
- preferred 亲和只是偏好，`SelectorSpreadPriority` 会让同 Service 的 Pod 分散。
- pod 反亲和用 required 时节点不够会 Pending。

## 三、命令速查

| 场景 | 命令 / 字段 | 说明 |
|---|---|---|
| 看节点资源 | `kubectl describe node <n>` | Capacity/Allocatable |
| 指定 requests | `resources.requests.cpu: 200m` / `.memory: 10Mi` | 200m=1/5 核 |
| 指定 limits | `resources.limits.cpu: "1"` / `.memory: 20Mi` | 1 核 = 1000m |
| 看 QoS | `kubectl describe pod` / `status.qosClass` | |
| 建 HPA | `kubectl autoscale deployment <n> --cpu-percent=30 --min=1 --max=5` | |
| 看 HPA | `kubectl get hpa` / `describe hpa <n>` | TARGETS 列 |
| 压测 Pod | `kubectl run -it --rm --restart=Never loadgenerator --image=busybox -- sh -c "while true; do wget -O- http://svc; done"` | |
| 看用量 | `kubectl top node / pod` | 实际使用量 |
| 加污点 | `kubectl taint node <n> node-type=prod:NoSchedule` | |
| 看污点/容忍 | `kubectl describe node/pod` | Taints 段 |
| 打标签 | `kubectl label node <n> gpu=true` | 亲缘性前提 |
| 节点不可调度 | `kubectl cordon <n>` / `uncordon <n>` | |
| 排空节点 | `kubectl drain <n>` | 疏散 Pod |
| PDB | `kubectl create poddisruptionbudget <n> --selector=app=kubia --min-available=3` | 保证最少可用 |
| 容忍字段 | `tolerations[].key/value/effect/operator/tolerationSeconds` | |
| 亲和字段 | `nodeAffinity.required.../preferred...`、`podAffinity`、`podAntiAffinity` + `topologyKey` | |

## 四、易错点

1. 调度只看 requests——节点 70% CPU 使用率也不影响调度（p.623）。
2. 容器内看到的是节点资源，不是自己的 limit（p.636）。
3. 内存超限必 OOMKilled；CPU 超限只是慢。
4. OOM 杀谁不看"谁超了"，看 QoS 和 OOM 分数（BestEffort 可能先死）。
5. `NoExecute` 不只阻调度，会驱逐已在运行的 Pod。
6. CPU 使用率可超 100%，是"实际/requests"。
7. preferred 亲和不是硬保证。

## 五、动手实践

1. 给 Deployment 的 Pod 配 requests（cpu 200m）+ limits（cpu 1），`kubectl describe pod` 看 QoS 等级（Burstable）。
2. 建 HPA（--cpu-percent=30），跑压测 Pod，`kubectl get hpa` 看 TARGETS 变化、副本自动增加；停压测看自动缩回。
3. 给一个节点加污点，建 Pod 观察 Pending；再加 toleration 看调度成功。
4. 用 nodeAffinity（required）把 Pod 强制调度到有 `gpu=true` 标签的节点。
5. 用 podAntiAffinity 把同 Service 的 Pod 分散到不同节点。
